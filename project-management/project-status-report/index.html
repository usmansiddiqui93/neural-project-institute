Project Status Report: How to Write One (With Examples)

A project status report is a short, regular update that tells stakeholders how a project is performing against its plan: what has been achieved, what comes next, how schedule, budget and scope are tracking, and which risks, issues and decisions need attention. A good one helps people make decisions; a weak one just lists activity. This guide shows you what to include, how to set RAG ratings, a step-by-step writing process and three worked examples you can copy.

Key takeaways

  • A status report exists to support decisions, so put the overall status and any decision request at the top.
  • Compare progress with the baseline: milestones, budget, scope and forecast, not just tasks completed.
  • Agree RAG definitions in advance, tie them to tolerances and always explain each colour in words.
  • Update the schedule, budget and RAID log first, then write the summary last.
  • Tailor the depth to the audience: one page for sponsors, more detail for the team, a short paragraph for executives.
  • Keep the format and send day consistent so readers can see trends from one report to the next.

What is a project status report?

A project status report is a regular, concise document in which the project manager summarises a project's current position against its approved plan. It covers progress since the last report, forecast dates and costs, scope changes, the most important risks and issues, and any decisions or help needed. Its purpose is to let stakeholders act early.

The report is a snapshot taken on a fixed status date. It compares actual performance with the project baseline for schedule, cost and scope, and adds the project manager's forecast of where the project will end up. Who receives it, how often and in what format should be agreed in the communication plan.

Different standards use different names for the same idea. PMI's PMBOK Guide refers to work performance reports: information compiled from project data to support awareness and decisions. PRINCE2 calls the regular report from the project manager to the project board a highlight report, with frequency set in the project initiation documentation. Whatever the name, the content is broadly the same.

A status report isA status report is not
A summary of progress against the planA list of every task the team touched
An honest forecast of time, cost and scopeA sales document for the project
A place to ask for decisions and helpA substitute for raising urgent problems straight away
Short, with links to detailThe full RAID log, schedule and budget pasted in

Why project status reports matter

A good status report earns back the time it takes to write:

  • Early warning. A forecast that a milestone will slip is far cheaper to act on four weeks out than four days out.
  • Faster decisions. When a sponsor sees a clear question with options and a deadline, they can answer it without a meeting.
  • Fewer status meetings and messages. Stakeholders stop chasing the team for updates when they know one arrives every Friday.
  • Trust. Consistent, honest reporting, including bad news, builds confidence in the project manager and the team.
  • An audit trail. A dated series of reports records what was known and decided, which supports project governance and audits.

Status reporting is one part of project communication management. Never let a serious problem wait for the next scheduled report.

What to include in a project status report

Most status reports, whatever the template, use the same core sections. The table below shows each one, what to put in it and a typical length.

SectionWhat to includeTypical length
HeaderProject name, reporting period and status date, author, sponsor, distributionOne line
Overall statusRAG rating, trend arrow and a one-line reasonOne line
Executive summaryWhere the project stands, what changed since last time and what matters mostTwo to four sentences
ScheduleKey milestones with baseline date, forecast date and statusThree to eight rows
BudgetBudget at completion, actual cost to date, forecast at completion and varianceOne small table
ScopeChange requests raised, approved or rejected this period; any signs of scope creepOne to three lines
Achievements this periodCompleted deliverables and milestones, not activityThree to five bullets
Planned next periodThe main outcomes the team expects to deliver nextThree to five bullets
Top risks and issuesThe three to five that matter now, each with owner, action and dateSmall table
Decisions or help neededWhat is needed, from whom and by when, with a recommendationOne to three items

Optional sections

Add these only when they help your audience decide something:

  • Benefits or KPIs: early indicators that the project will deliver its business case, such as adoption or volume figures.
  • Resources: vacancies, over-allocation or key leave that affects delivery.
  • Dependencies: inputs from other projects or suppliers that are late or at risk.
  • Earned value: schedule variance, cost variance and the CPI for projects that use earned value management.
  • Recognition: a short thank-you to people or teams who made a difference.
Tip

If a section has nothing new to say, write "No change" rather than deleting it. Readers then know you checked, and the layout stays consistent.

RAG status: how to rate red, amber and green

Most organisations rate status with red, amber and green (RAG). Some use yellow instead of amber, and some add blue for complete. The colours only work if everyone means the same thing by them, so define them in writing before the first report, ideally as a share of the agreed tolerance for time, cost and scope.

StatusMeaningExample thresholdWhat the reader should do
GreenOn track. Any problems are within the team's controlForecast uses less than half of the toleranceNothing; read for information
AmberAt risk. A recovery plan exists or attention is needed soonForecast uses between half and all of the tolerance, or a high risk is open without a working responseWatch closely; be ready to help
RedOff track. Outside tolerance, or will be without interventionForecast exceeds the toleranceDecide or intervene now

For example, if the sponsor has agreed a schedule tolerance of plus two weeks on the go-live date, a forecast slip of three days is green, a slip of eight days is amber, and a slip of three weeks is red.

Deciding the overall rating

Rate schedule, budget, scope, risks and quality separately first. Then use a simple rule for the overall status:

  1. Start from the worst individual rating.
  2. Move it down only if you can explain in one sentence why that area does not threaten the project as a whole, and say so in the report.
  3. Never rate the overall status green if any area is red.
  4. If you are unsure between two colours, choose the worse one and explain. Early amber is better than late red.

Add a trend and a forecast

A colour on its own shows the position today. Add a trend arrow (improving, stable or worsening) and, if useful, the forecast status at the next milestone. "Amber, improving" tells a very different story from "amber, worsening".

Tip

Never use colour alone. Write the status as a word as well as a colour, and give the reason, so readers with colour vision deficiency, or anyone printing in black and white, get the same message.

How to write a project status report step by step

The process below works for a weekly or monthly report. The order matters: update the data first and write the narrative last.

  1. Agree the basics once. In the communication plan, set the audience, frequency, send day, format and RAG definitions. Get the sponsor to confirm them.
  2. Fix the status date. Use a clear cut-off, such as close of business Thursday, so that schedule and cost figures relate to the same point in time.
  3. Collect inputs from the team. Ask work package or workstream leads for progress, forecast dates and new risks by a set time. A short form or a project tracker makes this quicker than chasing people.
  4. Update the plan and logs. Update the schedule, actual costs and forecast, the RAID log and the change control log. The report should summarise these sources, not replace them.
  5. Compare with the baseline. For each milestone, compare forecast with baseline. For the budget, compare forecast at completion with budget at completion. Note the variance and whether it is within tolerance.
  6. Rate each area and the overall status. Apply the agreed RAG definitions and the overall rule. Decide the trend.
  7. Choose the top risks and issues. Pick the three to five that could change a decision or a forecast. Each needs an owner, an action and a date.
  8. Write the decision request. State the decision, the options, your recommendation, the impact of delay and the date you need an answer.
  9. Write the summary last. In two to four sentences, say where the project stands, what changed and what you need. Read it aloud: if it would not make sense to the sponsor in a corridor, rewrite it.
  10. Check, send and follow up. Check figures against the source data, send on the agreed day and follow up any decision request personally.
Tip

A simple weekly rhythm works for most teams: team updates due Thursday midday, data and RAG ratings updated Thursday afternoon, report sent Friday midday, then walked through at the next project meeting so that time goes on decisions rather than updates.

Project status report example (weekly)

Here is a filled-in weekly report for a fictional customer portal project.

Project: Customer portal. Period: week ending 14 March. Author: project manager. Sponsor: head of customer service. Overall status: Amber, stable. Build is on track, but payment integration testing is blocked by supplier sandbox errors.

Summary: Account pages and invoice download are complete and tested. User acceptance testing (UAT) is forecast to start one week late because of a supplier defect in the payment sandbox. The go-live date is still achievable within tolerance if UAT starts by 28 March. Decision needed: sponsor to approve moving the UAT start by one week, by 17 March.

Monthly steering committee report example

A monthly report to a steering committee covers a longer period with less operational detail and more forecasting. On projects that use earned value, include the key indicators and say in plain words what they mean.

Project: Customer portal. Period: March. Overall status: Amber, worsening.

MeasureValueMeaning
Budget at completion (BAC)£480kApproved budget
Planned value (PV)£260kBudgeted cost of the work scheduled by 31 March
Earned value (EV)£240kBudgeted cost of the work actually completed
Actual cost (AC)£252kWhat that work has cost
Cost variance (CV = EV - AC)-£12k (-5%)Completed work has cost £12k more than budgeted
Schedule variance (SV = EV - PV)-£20kSlightly behind plan in value terms
Cost performance index (CPI = EV / AC)0.95About 95p of value for every £1 spent
Estimate at completion (EAC = BAC / CPI)£504kForecast final cost if current efficiency continues
Variance at completion (VAC = BAC - EAC)-£24kUses half of the £48k (10%) cost tolerance: amber

Summary for the committee: The portal is forecast to go live on 2 May as planned, but at £504k against a £480k budget, mainly because the payment integration needed more testing effort than estimated. The forecast is within cost tolerance. We recommend no change to plan; we will review again after UAT. No decision needed this month.

The EAC = BAC / CPI formula assumes current cost efficiency continues; if the cause has been fixed, say so and use a bottom-up forecast. Our cost performance index and estimate at completion guides explain these formulas in more depth.

Exception report example

An exception report is not a regular report. You raise it as soon as a forecast shows that a tolerance will be exceeded, rather than waiting for the next scheduled update. In PRINCE2, the project manager sends it to the project board, which decides how to respond.

Suppose the supplier's payment fix fails and the go-live forecast moves to 23 May, three weeks late against a two-week tolerance. A short exception report would cover:

  • Cause: the supplier's sandbox fix of 18 March failed retesting; the supplier now forecasts a fix on 8 April.
  • Impact: UAT cannot complete until 5 May; go-live forecast 23 May, one week beyond tolerance. Cost impact about £18k of extended team time.
  • Option A, accept the delay: go live 23 May; extra cost about £18k; no scope change.
  • Option B, reduce scope: launch on 2 May with card payments only and add direct debit in a later release; no extra cost; customers using direct debit keep the current process for six weeks.
  • Option C, add effort: bring in the supplier's senior integration team at about £30k; forecast go-live 9 May, within tolerance, but with a delivery risk.
  • Recommendation: Option B, because it protects the date that customer communications are built around and costs nothing extra.
  • Decision needed: by 1 April, to brief customer service in time.

The report gives options with consequences, not just bad news, which makes the board's decision quick.

How to write a status report for executives

Senior readers want the answer first. Use the "bottom line up front" approach: status, why, what you need.

  1. Status and trend: "Amber, stable."
  2. Reason in one sentence: "Go-live is on track, but UAT will start a week late because of a supplier defect."
  3. What you need: "Please approve the one-week UAT move by Tuesday."

Then give two or three lines of supporting facts and a link to the full report. Keep numbers to the few that drive decisions: the forecast go-live date, the forecast final cost against budget and any benefit at risk. An executive summary template can help you keep this discipline.

If the portfolio uses a standard one-line format for every project, follow it exactly. Your stakeholder management analysis will show which executives want more detail and which want less.

Writing good status updates: before and after

Most weak status reports are not wrong; they are vague. The table shows common weak lines and stronger rewrites.

WeakStrongerWhy it is better
"Testing is progressing well.""120 of 150 test cases passed; on track to finish by 25 March."Measurable and tied to a date
"Some delays with the supplier.""Supplier fix is five days late; UAT start moves from 21 to 28 March."States the impact on a milestone
"Worked on the data migration.""Migrated 3 of 5 customer data sets; remaining 2 due 20 March."Shows progress, not activity
"Budget is fine.""£212k spent of £480k; forecast £470k, within budget."Gives actual, forecast and comparison
"Risk around resources.""Risk: no UAT testers confirmed for month-end. Owner: sponsor. Action: name testers by 20 March."Specific, owned and dated
"We may need more money.""Decision: approve £18k contingency release by 1 April, or go-live slips to 23 May."A clear ask with a deadline and consequence

Status reports on Agile projects

Agile teams still need to tell stakeholders how things are going, but the format changes. Scope is expected to flex, so "percentage complete against a fixed plan" is less meaningful. Instead, report:

  • Sprint or iteration goal: met, partly met or not met, with the reason.
  • What was delivered: the increment and any features released to users.
  • Release or roadmap forecast: a burnup chart showing completed work against total scope, with a forecast date range rather than a single date.
  • Flow measures: cycle time and throughput for teams using Kanban.
  • Impediments and dependencies that need help from outside the team.
  • Outcome measures: usage, customer feedback or other evidence that the product is delivering value.

Treat velocity as a team planning aid, not a productivity score to compare between teams. The sprint review is where stakeholders inspect the increment and adapt the backlog; it is a working session, not a status meeting, so a short written update often accompanies it rather than replacing it.

Status report vs progress report vs highlight report

These terms are often used interchangeably. Where organisations do draw a distinction, it usually looks like this:

ReportPurposeTypical author and audienceFrequency
Status reportSnapshot of where the project stands against plan, with forecasts and decisionsProject manager to sponsor and stakeholdersRegular, often weekly or monthly
Progress reportWhat work has been completed over a period; often more detailed and team-focusedTeam lead or project manager to project manager or clientRegular
Highlight report (PRINCE2)Regular summary of stage status for the project boardProject manager to project boardAs set in the project initiation documentation
Checkpoint report (PRINCE2)Progress of a work package against agreed targetsTeam manager to project managerAs set in the work package
Exception reportNotice that a tolerance is forecast to be breached, with optionsProject manager to sponsor or boardOnly when needed

A dashboard and a status report work well together: the dashboard shows the numbers at any time, and the status report adds the project manager's interpretation, forecast and requests.

Common mistakes (and how to avoid them)

MistakeWhy it happensHow to avoid it
Watermelon reporting: green outside, red insideVague RAG definitions, fear of bad news, optimismTie RAG to tolerances; praise early warnings; ask "what would make this red?"
Listing activity instead of progressActivity is easier to reportReport against milestones and deliverables
Burying the decision requestTemplates put it lastPut decisions in the summary at the top
Listing every riskFear of missing somethingReport the top three to five; link to the full risk register
Stale dataReport written before logs are updatedUpdate schedule, costs and RAID log first
Changing the format each timeDifferent authors, or tinkeringFix a template and keep it for the life of the project
Undefined percentage complete"90% done" for weeksUse milestones or objective rules such as 0/50/100
No owners or dates on actionsWriting in a hurryEvery risk, issue and action has a named owner and a date

Watermelon projects are rarely caused by dishonesty; more often a project manager hopes to recover before anyone notices. Sponsors who respond to early amber with help rather than blame get earlier, more honest reports.

Status report checklist before you send

  • The status date and reporting period are stated.
  • The overall RAG rating has a trend and a one-line reason.
  • The summary is four sentences or fewer and makes sense on its own.
  • Every milestone shows baseline and forecast dates.
  • Budget shows actual to date, forecast at completion and variance against budget.
  • No more than five risks and issues, each with an owner, action and date.
  • Any decision request says what, who, by when and what happens if it is late.
  • The report fits on one page or one screen, with links to detail.
  • Nothing in it will surprise the sponsor: anything red has been discussed in person first.

Tools and templates for status reporting

You do not need special software to write a good status report. A consistent template and current source data matter more. Free templates that help:

  • Project tracker template to collect task status, owners and progress.
  • RAID log template and risk register template for the risks and issues section.
  • Project schedule template for milestone dates and forecasts.
  • Communication plan template to agree who gets which report and when.
  • Executive summary template for the senior-audience version.

As a project grows, project management software can save a lot of collection time. Most tools now offer dashboards, project status fields and automated status updates, and some generate draft summaries with AI. Wrike, our top-ranked tool, combines dashboards, custom reports and portfolio views, which suits teams reporting across many projects; see our Wrike review. Whichever tool you use, keep a short written summary from the project manager: software can show the numbers, but it cannot judge which risk matters most or what you need the sponsor to decide.

Frequently asked questions

What is a project status report?

A regular, concise update from the project manager that summarises progress against the plan, forecast dates and costs, scope changes, top risks and issues, and any decisions needed from stakeholders.

What should be included in a project status report?

Overall RAG status with a reason, a short summary, milestones, budget and forecast, scope changes, achievements, next steps, top risks and issues, and decisions needed.

How do you write a weekly status report?

Fix a status date, update the schedule, costs and RAID log, rate each area against agreed RAG definitions, write any decision request, write the summary last and send it on the same day each week.

How often should a project status report be sent?

Weekly is common for active projects; fortnightly or monthly suits longer, steadier projects or senior audiences. Agree it in the communication plan.

What does RAG status mean?

Red, amber, green: a rating of whether the project or an area is off track, at risk or on track. Define each colour in advance and always explain it in words.

How long should a project status report be?

Ideally one page or one screen, with links to detail. Executive versions can be three to five lines.

Who writes the project status report?

The project manager, using inputs from workstream leads and the project's schedule, cost data and logs.

What is the difference between a status report and a progress report?

The terms are often used interchangeably. Where they differ, a progress report records work completed over a period, while a status report gives a snapshot against plan with forecasts and decisions.

Is a highlight report the same as a status report?

Broadly, yes. Highlight report is the PRINCE2 name for the project manager's regular summary of stage status to the project board.

What is an exception report?

A report raised only when a forecast shows an agreed tolerance will be exceeded. It explains the cause and impact and gives options with a recommendation.

What is a watermelon project?

A project reported as green while the reality underneath is red. It usually comes from vague RAG definitions, optimism or reluctance to share bad news.

How do I write a status report for executives?

Lead with the status and trend, give the reason in one sentence, then state what you need and by when. Link to the full report.

How do you report status on an Agile project?

Report the sprint goal result, what was delivered, a burnup-based release forecast with a date range, impediments and outcome measures, rather than percentage complete against a fixed plan.

Can project management software create status reports?

Yes. Many tools offer dashboards and automated or AI-drafted updates, but a short written summary from the project manager is still valuable.
