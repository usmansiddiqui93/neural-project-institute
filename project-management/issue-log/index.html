Issue Log: Template, Examples and How to Manage Issues

An issue log is the single record a project keeps of problems, concerns and requests that are affecting it now, with a priority, an owner, agreed actions and a status for each one. Kept well, it means nothing raised is forgotten and every issue is resolved, escalated or closed on purpose. This guide covers the columns to use, how to prioritise and escalate, a worked example from capture to closure and a full sample log.

Key takeaways

  • An issue is something that is happening now or is certain to happen; a risk is something that might happen. Keep them in different places, or clearly typed in one RAID log.
  • Every entry needs a factual description, an impact, a priority, one named owner, a next action with a date and a status.
  • Define priority levels in plain terms (for example, 'critical' means critical-path work has stopped) so two people would rate the same issue the same way.
  • Escalate by rule, not by feel: when resolving the issue would breach an agreed time, cost or scope tolerance, or needs a decision above your authority.
  • If fixing an issue would change the scope, schedule or cost baseline, raise a change request and link it to the issue.
  • Review the log every week, report the high-priority items and their age, and mine closed issues for lessons learned.

What is an issue log?

An issue log is a project document that records every current issue (a problem, concern, query or request already affecting the project) together with its impact, priority, owner, agreed actions, target date and status. Its purpose is to make sure each issue is visible, has someone responsible for it and reaches a deliberate outcome: resolved, escalated or closed.

The log is usually a table: one row per issue, one column per piece of information. It can live in a spreadsheet, a shared document or a project management tool. What matters is that there is only one log for the project and that everyone knows where it is.

The term is used in the PMBOK Guide, where the issue log is one of the project documents updated throughout execution. PRINCE2 uses the name issue register for formally managed issues. Both mean essentially the same thing. Some organisations call it an issue tracker or issues list.

What counts as an issue

An issue is anything that is already affecting the project, or is certain to, and needs someone to act or decide. PRINCE2 7 describes issues very broadly, as anything that could affect the project, and groups them into a few types that are useful on any project:

TypeWhat it meansExample
ProblemSomething has gone wrong or is blocking workThe test environment has been down for two days
ConcernA stakeholder is worried about something and wants it addressedThe finance director doubts the new invoice layout meets audit rules
Off-specificationA deliverable does not meet, or will not meet, its agreed requirements2,000 printed labels carry the old logo
Request for changeSomeone wants a baseline (scope, requirements, dates) changedMarketing asks for a second language on the website
OpportunitySomething certain and beneficial that was not in the planA supplier offers to deliver a week early at no extra cost

Many teams record requests for change in a separate change log and handle them through change control. That is fine, as long as the issue log points to the change request when an issue leads to one.

What does not belong in the issue log

  • Risks: uncertain future events belong in the risk register until they happen.
  • Routine tasks: "Send the weekly report" is a task, not an issue. Put it in the plan or an action list.
  • Every individual bug: product defects are normally tracked in a defect or bug tracker. Log a defect as a project issue only when it threatens a milestone, the budget or acceptance.
  • Decisions already made: record these in a decision log. The issue log can reference the decision that resolved an issue.

Why keep an issue log?

Problems surface on every project. Whether a project recovers usually depends on whether they are written down, owned and followed up. An issue log gives you:

  • Visibility: one place where the project manager, team and sponsor can see what is going wrong and how serious it is.
  • Accountability: each issue has a single owner and a date, so issues do not sit unanswered in email threads.
  • Faster decisions: with impact and options recorded, the person who needs to decide can do so quickly.
  • Patterns: several issues with the same cause point to a deeper problem worth analysing with a fishbone diagram or root cause analysis.
  • Lessons learned: closed issues are the most honest record of what went wrong and are a strong input to lessons learned.

Issue log vs risk register, change log and other logs

Most confusion about issue logs comes from mixing up issues with the other things a project tracks. Use this table to decide where an item belongs.

ItemDefinitionQuestion it answersWhere it is recorded
IssueA current problem, concern or request that needs actionWhat is wrong now and who is fixing it?Issue log
RiskAn uncertain event that might affect objectivesWhat might happen and what will we do about it?Risk register
Change requestA formal proposal to change an agreed baselineShould we change scope, time or cost?Change log, through change control
DefectA fault in a product or deliverableWhat does not work as specified?Defect or bug tracker
ActionA task agreed in a meetingWho will do what by when?Action log or meeting notes
DecisionA choice made by someone with authorityWhat was decided, by whom and why?Decision log

When a risk becomes an issue

If a risk occurs, it is no longer uncertain, so it becomes an issue. Close the risk in the register with a status such as "occurred", open a new entry in the issue log, and put each ID in the other entry so the link is clear. If a contingency plan was prepared for that risk, the first action on the issue is usually to trigger it.

When an issue becomes a change request

Some issues can only be fixed by changing what was agreed: extra scope, a later date or more money. At that point the issue owner (often with the project manager) raises a change request and the decision moves into change control. The issue stays open, with status "escalated" or "awaiting decision", until the change is approved or rejected. This keeps the trail from problem to decision intact. A useful test from PRINCE2 7 guidance is that an issue only becomes a change once you know it will affect a baseline.

Issue log vs RAID log

A RAID log combines Risks, Assumptions, Issues and Dependencies in one table, with a type column. It suits small and medium projects where one view is easier to review. Larger projects, or projects with many issues, usually keep a dedicated issue log with more columns and report a RAID summary to the sponsor.

Start with the core columns below. They are enough for most projects, and adding more before you need them only makes the log harder to keep current.

ImpactEffect on time, cost, scope, quality or benefitsSystem testing finish date at risk by up to 5 days

Optional columns for larger projects

  • Category or workstream: technical, supplier, people, environment, stakeholder; useful for spotting patterns.
  • Severity and urgency as separate fields, if you calculate priority from them (see below).
  • Escalated to and date: who now holds the decision.
  • Linked items: risk ID, change request ID, defect ID, affected milestone or work package.
  • Root cause: completed on closure; this is what makes the log useful for lessons learned.

How to write a good issue description

A good description lets someone who was not in the room understand the issue and judge its priority. Use three parts: the condition (what is happening), the evidence (how you know) and the consequence (what it is doing to the project).

WeakStrong
Supplier problemsSupplier has delivered 300 of 1,000 chairs due on 10 June; remaining 700 now promised for 24 June, after the office opening on 17 June
Testing delayedUAT cannot start: 6 of 9 test users have not received system access; access requests raised 28 May, still pending with IT security
Tip

Keep descriptions factual and free of blame. Write about the situation, not the person. People stop raising issues quickly if the log becomes a record of who to blame.

How to prioritise issues

Priority decides what gets attention first, so it is worth agreeing the definitions at the start of the project and writing them at the top of the log. A practical approach is to rate two things separately and combine them:

  • Severity: how much damage the issue does, or will do, to objectives if nothing changes.
  • Urgency: how soon that damage happens, or how soon a decision is needed.
Urgency: needs action within daysUrgency: needs action within weeksUrgency: can wait
Severity: high (milestone, budget or acceptance threatened)CriticalHighMedium
Severity: medium (workaround exists, some delay or extra cost)HighMediumLow
Severity: low (minor inconvenience)MediumLowLow

Then define what each priority means in practice, and how quickly it should be handled. The response times below are our suggestions; adjust them to your project's length and governance.

PriorityPlain-language definitionFirst responseReview
CriticalCritical-path work has stopped, a key milestone or legal requirement will be missed, or cost overrun exceeds toleranceSame day; sponsor informedDaily until resolved
HighA milestone or the budget is threatened, or a major deliverable will fail acceptance without actionWithin 2 working daysAt least twice a week
MediumWork is slowed or extra effort is needed, but a workaround exists and no milestone is at risk yetWithin 1 weekWeekly
LowMinor inconvenience; can be fixed when convenientWhen capacity allowsWeekly or fortnightly

Priority vs severity

Severity describes how bad the effect is; priority describes the order in which you will deal with it. A severe issue that will not bite for two months can be lower priority than a medium issue blocking today's work. Recording both helps explain your choices to stakeholders.

Issue statuses and what they mean

Statuses only help if everyone uses them the same way. Agree a short list with clear entry and exit rules:

StatusMeansMoves on when
OpenLogged, not yet assessed or assignedPriority and owner are agreed
In progressOwner is working on actionsFix is delivered, or escalation is needed
EscalatedDecision or resources needed from above the project managerThe decision is made and actions are agreed
On holdDeliberately parked, with a reason and a review dateThe review date arrives or circumstances change
ResolvedThe fix is in placeThe person who raised it confirms the problem has gone
ClosedConfirmed resolved, or formally accepted with no further actionFinal; reopen as a new linked issue if it returns

The difference between resolved and closed is important. Resolved means the owner believes it is fixed; closed means the fix has been checked, the person who raised it agrees, and the resolution has been written up. Skipping the check is how the same issue comes back a fortnight later.

How to manage issues step by step

The process below works for most projects. It mirrors the capture, assess, decide and implement pattern used in PRINCE2 and most organisational issue procedures.

  1. Capture: log the issue as soon as it is raised, even if it seems small. Anyone on the project should be able to raise one, either directly in the log or by telling the project manager.
  2. Triage: within the agreed response time, confirm it really is an issue (not a risk, task or defect), check it is not a duplicate, and set type and priority.
  3. Assign: give the issue one owner. The owner is accountable for driving it to resolution, even if other people do the work.
  4. Analyse: the owner confirms the impact and identifies options. For anything significant, find the cause, not just the symptom.
  5. Act: agree the next action and a date. Check whether a contingency plan already covers it.
  6. Escalate if needed: if the fix needs authority, money or decisions beyond the project manager's tolerances, escalate (see the next section). If it changes a baseline, raise a change request.
  7. Monitor: update the next action and status at least as often as the priority requires; review the whole log weekly.
  8. Close: confirm the fix with the person who raised it, record the resolution and root cause, and note any lesson worth sharing.

The project manager owns the log and the review; each issue owner keeps their own entries current; the sponsor or board decides escalated issues. If those roles are unclear on your project, a RACI matrix for the issue process takes ten minutes and prevents a lot of argument.

When and how to escalate an issue

Escalation is not failure. It is the mechanism that gets a decision made by the person with the authority to make it. The problem is usually escalating too late. Agree escalation rules with the sponsor at the start, ideally as part of your project governance, and tie them to tolerances:

TriggerExample ruleEscalate to
TimeResolution would delay a key milestone by more than 5 working daysSponsor
CostResolution needs more than the project manager's contingency, e.g. above 2,000Sponsor or board
Scope or qualityResolution means dropping or changing an agreed deliverable or acceptance criterionBoard, through change control
AuthorityNeeds a decision from another department, a supplier's management or a contract changeSponsor
AgeingA high-priority issue has had no progress for 5 working daysNext level up from the owner
Reputation, safety or legalAny issue with safety, legal or regulatory exposureSponsor immediately

The figures above are illustrative; set your own. When you escalate, send a short note that the decision-maker can act on without a meeting:

  • The issue in one sentence, and its ID.
  • The impact if nothing is done, in days, money or scope.
  • What has already been tried.
  • Two or three options with their consequences, and your recommendation.
  • The decision you need and the date you need it by.

Record the escalation in the log (status "escalated", escalated to, date) and keep chasing until there is a decision.

Worked example: one issue from capture to closure

Here is how a single issue moves through the log on an office relocation project. The project moves 120 staff to a new building, with the move weekend fixed for 14 June because the old lease ends that month.

DateEventLog update
20 MayThe furniture supplier emails that 700 of 1,000 desks will arrive on 24 June, not 10 JuneI-021 logged by the facilities coordinator. Type: problem. Status: open
20 MayProject manager triages the same afternoonImpact: 70 per cent of staff without desks on day one; move date at risk. Severity high, urgency within days, so priority critical. Owner: procurement lead
21 MayOwner contacts the supplier and two alternativesNext action: get quotes for hiring 700 temporary desks; due 23 May. Status: in progress
23 MayHire costs 6,500; project manager's contingency is 4,000Cost tolerance would be breached, so the issue is escalated to the sponsor with three options: hire desks, phase the move, or delay the move a week
24 MaySponsor approves hiring desks for 300 staff and moving one department a week laterDecision recorded and linked to change request CR-006 (phased move). Status: in progress
14 JuneMove completes; hired desks in placeStatus: resolved
26 JunePermanent desks installed; facilities coordinator confirms no outstanding problemsStatus: closed. Root cause: supplier capacity not checked at contract stage. Lesson: add capacity confirmation to supplier onboarding

Three points from the example. First, triage was the same day, which is what a critical rating demands. Second, the escalation was triggered by a pre-agreed cost tolerance, so nobody had to argue about whether to involve the sponsor. Third, the closed entry captures a root cause and a lesson, which is where most of the long-term value of an issue log comes from.

Reviewing the issue log and reporting it

An issue log is only useful while it is current. Put a review on the agenda of your weekly project meeting, and keep it short by following the same order each time:

  1. New issues since last week: confirm type, priority and owner.
  2. Critical and high issues: progress, next action, any escalation needed.
  3. Overdue actions: why, and a new date or an escalation.
  4. Issues on hold: is the review date due?
  5. Resolved issues: confirm and close.
  6. Patterns: any repeated causes, categories or owners?

Issue log health measures

A few simple counts tell you, and your sponsor, whether issues are under control. Our suggestions:

MeasureWhat it shows
Open issues by priorityCurrent exposure; a growing count of high and critical items is an early warning
Average age of open high and critical issuesWhether serious issues are actually being resolved
Issues with overdue next actionsWhether owners are following through
Issues opened vs closed this periodWhether the project is catching up or falling behind
Issues with no update in two weeksStale entries that need challenging

In the project status report, list critical and high issues with their impact and next step, state any decisions you need, and give the counts above. Do not paste the whole log into the report.

Issue logs in Agile teams

Agile teams deal with most day-to-day issues as impediments or blockers. They are flagged on the board, raised at the daily scrum and removed quickly, often by the Scrum Master. A heavyweight log for these would slow the team down.

A light issue log is still useful for issues the team cannot remove on its own, such as other-team dependencies, supplier problems or anything needing escalation. An impediment list with an owner and date is an issue log by another name.

One terminology trap: in Jira, everything tracked used to be called an "issue", including stories, tasks and bugs. During 2025 Atlassian began using "work item" as the collective term in Jira Cloud. Either way, a Jira issue or work item is not necessarily a project issue in the sense used here. If you track project issues in Jira, create a dedicated type or label for them.

Issue log in PMBOK and PRINCE2

If you are studying for an exam, the vocabulary differs slightly between the two main bodies of guidance.

PMBOK Guide (PMI)PRINCE2 7 (PeopleCert / AXELOS)
NameIssue logIssue register for formal issues; informal issues are noted in the daily log
Issue typesNot formally typedRequest for change, off-specification, problem or concern, and business opportunity
ProcessIssues are managed as part of directing and monitoring the workCapture, assess, propose, decide, implement
Who decidesProject manager, escalating via governanceProject manager within tolerance; a change authority or the project board beyond it

Whichever method you follow, the practice is the same: log it, own it, assess it, decide, act and close. For more on each method, see our guides to the PMBOK Guide and PRINCE2.

Tools for keeping an issue log

A spreadsheet is enough for most single projects. It is quick to set up, everyone can open it and filtering by owner or priority is easy. Move to a project management tool when you need automatic reminders, issues linked to tasks and milestones, request forms for raising issues, or a portfolio view across many projects.

Frequently asked questions

What is an issue log in project management?

An issue log is a project document that lists every current problem, concern or request affecting the project, with its impact, priority, owner, actions, target date and status, so that each one is resolved, escalated or closed deliberately.

What should an issue log include?

At minimum: ID, date raised, raised by, description, impact, priority, owner, next action with a date, target resolution date, status and resolution. Larger projects often add type, category, escalation details, linked risk or change IDs and root cause.

What is the difference between an issue log and a risk register?

An issue log tracks problems that are happening now or are certain; a risk register tracks uncertain events that might happen. When a risk occurs, close it in the register and open a linked issue.

Who is responsible for the issue log?

The project manager (or a project coordinator) owns and maintains the log. Each issue owner keeps their own entries up to date, and the sponsor or board decides escalated issues.

How do you create an issue log?

Agree the columns, priority definitions and status list; set up a shared spreadsheet or tool; explain to the team how to raise issues; then log, triage and review issues weekly. Starting from a template such as our RAID log template saves time.

How often should an issue log be updated?

Update entries whenever something changes, and review the whole log at least weekly. Critical issues may need a daily update until they are resolved.

What priority levels should an issue log use?

Four levels (critical, high, medium, low) work for most projects, provided each has a plain-language definition and a target response time. Many teams derive priority from severity and urgency.

When should an issue be escalated?

When resolving it would breach an agreed time, cost, scope or quality tolerance, needs a decision outside the project manager's authority, involves safety or legal exposure, or a high-priority issue has stalled.

What is the difference between an issue log and a RAID log?

A RAID log tracks risks, assumptions, issues and dependencies in one table. An issue log covers issues only, usually in more detail. Smaller projects often use just a RAID log.

Is an issue log the same as a change log?

No. An issue log records problems and requests; a change log records formal change requests and their decisions. An issue that needs a baseline change leads to a change request, and the two entries should be linked.

What is an issue log in PMP?

In the PMBOK Guide, which underpins the PMP exam, the issue log is a project document used to record and monitor issues, their owners and their resolution, and it is updated throughout execution.

What is an issue register in PRINCE2?

It is PRINCE2's name for the log of formally managed issues. Each formal issue gets an ID and may have an issue report with impact analysis and options. Informal issues are handled by the project manager and noted in the daily log.

Can I keep an issue log in Excel or Google Sheets?

Yes. A spreadsheet works well for most projects. Use dropdowns for type, priority and status, freeze the header row and filter by owner. Move to a project management tool when you need reminders, forms or cross-project reporting.

Should closed issues be deleted from the log?

No. Filter them out of the working view but keep them. Closed issues provide the audit trail and are a valuable input to lessons learned.
