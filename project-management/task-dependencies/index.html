Task Dependencies: Types, Examples and How to Manage Them

Task dependencies are the logical links between activities that decide when one activity can start or finish relative to another. They turn a list of tasks into a schedule that can calculate dates, find the critical path and show how far a delay will spread.

Written byNeural Project InstituteProject management editorial team
  • Published 23 September 2026
  • Last updated 14 October 2026
  • 20 min read

Key takeaways

  • A task dependency links a predecessor to a successor and says which end of one controls which end of the other.
  • There are four types: finish-to-start (by far the most common), start-to-start, finish-to-finish and start-to-finish (rare).
  • Dependencies are also classified as mandatory or discretionary, and internal or external; discretionary links are your main lever when you need to shorten a schedule.
  • Find dependencies by asking two questions of every activity: what must happen before this, and what is waiting for it?
  • Give every external dependency a named owner and review it at each status meeting.
  • Let dependencies drive dates. Typing dates in by hand hides the logic and breaks the critical path.

What is a task dependency?

A task dependency is a logical relationship between two activities in which the start or finish of one activity (the successor) depends on the start or finish of another (the predecessor). Dependencies set the order of work, and once durations are added they allow a schedule to calculate dates, float and the critical path.

The simplest example: you cannot print a brochure until the text has been proofread. "Proofread" is the predecessor, "Print" is the successor, and the link between them is a finish-to-start dependency. If proofreading slips by two days, printing slips by two days too, unless you change the plan.

Dependencies are one of the three building blocks of a schedule, alongside the activity list and the duration estimates. If you have not yet broken the work down, start with the work breakdown structure and the activity list, then add the links.

Key terms

TermMeaning
PredecessorThe activity that comes first and controls the timing of the other
SuccessorThe activity that depends on the predecessor
Link typeWhich end of the predecessor controls which end of the successor: FS, SS, FF or SF
LagA deliberate wait added to a link, such as 3 days for concrete to cure
LeadAn overlap on a link, written as a negative lag, such as FS-2 days
Driving predecessorWhen an activity has several predecessors, the one that actually sets its start date
Float (slack)How long an activity can slip without delaying the project end date
Critical pathThe longest chain of dependent activities, which sets the shortest possible project duration

The two ends of a link are covered in detail in our guide to predecessors and successors.

Why task dependencies matter

A task list with durations but no dependencies is just a list. Once the links are in place, the schedule starts doing useful work for you:

  • Realistic dates: start and finish dates are calculated from the logic rather than guessed.
  • A critical path: tools use the links to run the forward and backward pass and show which activities have zero float.
  • Delay forecasting: when an activity slips, every affected successor moves, so you see the knock-on effect straight away.
  • Clear hand-offs and risks: each link is a hand-off between people, and external links (suppliers, approvals) are early warnings of likely delay.
  • What-if analysis: you can test overlapping activities or removing a preferred sequence before you commit.

The four types of task dependencies

Every dependency joins one end of the predecessor (its start or its finish) to one end of the successor. That gives four possible combinations, known as the four logical relationships.

TypeRuleExampleNotationHow common
Finish-to-start (FS)The successor cannot start until the predecessor finishesPour the foundations, then build the wallsB: A FSBy far the most common; the default in most tools
Start-to-start (SS)The successor cannot start until the predecessor startsStart editing chapters once writing has startedB: A SSCommon for overlapping work
Finish-to-finish (FF)The successor cannot finish until the predecessor finishesTesting cannot finish until development finishesB: A FFCommon for parallel work that must end together
Start-to-finish (SF)The successor cannot finish until the predecessor startsThe old system keeps running until the new one goes liveB: A SFRare; often a sign the logic can be written more simply

Finish-to-start (FS)

The successor waits for the predecessor to be complete. Use FS when the successor genuinely needs the output of the predecessor: you need approved designs before you build, a signed contract before you order materials, and data migration finished before user acceptance testing. Most schedules are made up mainly of FS links, and it is the default when you link tasks in tools such as Microsoft Project, Smartsheet or Wrike.

Start-to-start (SS)

The successor can begin once the predecessor has begun, so the two run in parallel. SS links usually carry a lag: "start laying cables two days after trenching starts" is SS+2 days. SS is useful when work can flow in batches, for example when an editor can start on chapter one while the author writes chapter two.

Finish-to-finish (FF)

The successor cannot be completed until the predecessor is complete. The two activities may start at different times, but their finishes are tied. A common example is documentation that cannot be finished until the feature it describes is finished. FF links are often paired with an SS link on the same two activities to model overlapping work properly.

Start-to-finish (SF)

The successor cannot finish until the predecessor starts. The classic example is a hand-over: the night security shift cannot end until the day shift has started, and an old system cannot be switched off until the new one is live. SF is rare in real schedules. If you find yourself using it, check whether an FS link with the activities the other way round says the same thing more clearly.

Tip

Default to finish-to-start. Use SS and FF only when the work really can overlap, and record why. Overlaps shorten the schedule but add risk, because the successor starts on incomplete information.

Leads and lags on a dependency

Any of the four link types can carry a timing adjustment:

  • Lag is a wait between the predecessor and the successor. Plaster must dry for 3 days before painting: Paint depends on Plaster FS+3 days.
  • Lead is an overlap. Testers can start 2 days before development finishes: Test depends on Develop FS-2 days. Most tools record a lead as a negative lag.
  • SS and FF lags offset the starts or finishes: Proofread SS+2 days means proofreading starts two days after writing starts.

A lag is waiting time, not work. If someone has to do something during the gap, such as inspect the concrete, make it an activity with an owner rather than hiding it in a lag. Our guide to leads and lags has more worked examples.

Mandatory, discretionary, internal and external dependencies

The four link types describe timing. A second way to classify dependencies describes why the link exists and who controls it. The PMBOK Guide (Sixth Edition) describes four attributes, which are used in pairs: every dependency is either mandatory or discretionary, and either internal or external.

Internal (within the team's control)External (outside the project)
Mandatory (hard logic)You cannot test code that has not been writtenYou cannot open a building before the fire safety certificate is issued
Discretionary (soft logic)The team prefers to finish the design before starting the buildThe client prefers to approve each phase before the next starts, though the contract does not require it
  • Mandatory dependencies are required by the nature of the work, the law or a contract. They are also called hard logic. You cannot remove them without changing the work itself.
  • Discretionary dependencies reflect best practice, experience or a preferred sequence. They are also called soft logic or preferential logic. They can be changed, usually at the price of more risk.
  • External dependencies involve something outside the project: suppliers, regulators, other projects, the client. The project team cannot control them, only monitor and influence them.
  • Internal dependencies are between activities the project controls.

Discretionary dependencies are the first place to look when you need to shorten the schedule. Overlapping two activities that were in sequence only by preference is called fast tracking; see fast tracking vs crashing. Document why each discretionary link exists, so you know what risk you take on by changing it.

Other labels you will meet

  • Resource dependency: two activities could run in parallel, but the same person or machine is needed for both, so one has to wait. Many planners handle this through resource levelling rather than a logical link.
  • Cross-team dependency: one team needs a deliverable from another team, common in Agile programmes and large organisations.
  • Logical dependency: another name for a mandatory link driven by the nature of the work.
  • Preferential dependency: another name for a discretionary link.

Dependencies vs constraints, blockers and risks

These terms are often used interchangeably, but they mean different things and are managed differently.

TermWhat it isExampleWhere to record it
DependencyA logical link between two activitiesInstall software after hardware set-upSchedule (predecessor column)
ConstraintA limit placed on an activity or the project, such as a fixed date, budget or resource capExhibition opens on 4 May; budget is capped at £50,000Schedule date constraint, project charter; see project constraints
BlockerSomething stopping work right nowThe test environment is downIssue log or board, raised at the stand-up
RiskAn uncertain event that may affect the projectThe supplier may deliver lateRisk register

An external dependency often creates a risk (it might be late) and, when it is late, a blocker. Many teams track all of these together in a RAID log, which stands for risks, assumptions, issues and dependencies.

How to identify task dependencies, step by step

Dependencies are easiest to find in a short workshop with the people who will do the work, using sticky notes or a shared whiteboard.

  1. Start from the activity list. Make sure each activity is a clear piece of work with an owner and a deliverable. Vague activities produce vague links.
  2. Ask the backward question. For each activity: what must be finished, started or available before this can start? Those are its predecessors.
  3. Ask the forward question. For each activity: what is waiting for this? Those are its successors. Asking both questions catches links that one question misses.
  4. Choose the link type. Default to finish-to-start. Use SS or FF only if the work can genuinely overlap, and agree the lag.
  5. Classify the link. Mark it mandatory or discretionary and internal or external, and note the reason in a comment.
  6. Find the external dependencies. Walk through suppliers, approvals, other projects, client inputs and shared environments. Add each as a milestone or activity with an owner.
  7. Check the network. Draw or generate a network diagram. Every activity except the start and finish should have at least one predecessor and one successor, and there should be no loops.

Useful prompts for the workshop:

  • What information, approval or material does this activity need?
  • Who hands work to you, and who do you hand it to?
  • Is this order required, or is it just how we usually do it?
  • Does anything outside the team have to happen first?
  • Could part of this start before the previous activity is fully complete?

How to record task dependencies

Record dependencies in a consistent format so they can be checked, reviewed and entered into a tool. A simple dependency table is enough for most projects.

Predecessor notation in scheduling tools

Microsoft Project and several other tools use a compact notation in the Predecessors column: the predecessor's ID, then the link type, then any lag or lead. A bare ID means finish-to-start with no lag.

Dependency matrix

On programmes with many teams, a dependency matrix gives an overview. List teams or workstreams down the side and across the top, and in each cell note what the row team needs from the column team and by when. It quickly shows which teams are heavily depended on and where to focus coordination.

Worked example: an office move

A small team is relocating to a new office. The activities, durations and dependencies are below. Durations are in working days, and day 0 is the start of the project.

IDActivityDurationPredecessorsCategory
AConfirm floor plan3NoneStart
BOrder furniture2A FSMandatory, internal
CFurniture delivery (supplier)10B FSMandatory, external
DInstall network cabling5A FSMandatory, internal
EInstall furniture3C FSMandatory, internal
FSet up IT equipment4D FS; E SS+1Mandatory; discretionary
GPack old office4E SSDiscretionary
HMove day1E FS; F FS; G FSMandatory
ISnagging and handover2H FSMandatory

Step 1: calculate the dates

Work forward through the network. Each activity starts at the latest date allowed by all of its predecessors (its driving predecessor sets the date).

ActivityStartFinishDriving predecessor and why
A Confirm floor plan03Project start
B Order furniture35A finishes on day 3
C Furniture delivery515B finishes on day 5
D Network cabling38A finishes on day 3
E Install furniture1518C finishes on day 15
F Set up IT1620E starts on day 15, plus 1 day lag = 16, which is later than D's finish on day 8
G Pack old office1519E starts on day 15
H Move day2021F finishes on day 20, later than E (18) and G (19)
I Snagging and handover2123H finishes on day 21

The project takes 23 working days.

Step 2: find the critical path and float

The critical path is A → B → C → E → F → H → I, running through the furniture supplier. These activities have zero float: any delay to them delays the move.

  • D Network cabling finishes on day 8 but F does not need it until day 16, so D has 8 days of float. A slip of a few days in cabling does not matter.
  • G Pack old office finishes on day 19 and the move starts on day 20, so G has 1 day of float.
  • The furniture delivery, an external dependency, is on the critical path. That tells the project manager exactly where to spend attention: confirm the order early and chase the supplier.

For the full method, see the critical path method and forward and backward pass guides.

Step 3: test a delay

The supplier calls on day 8: delivery will take 15 days, not 10. Because the links are in place, the schedule recalculates on its own. C now finishes on day 20, E runs 20 to 23, F runs 21 to 25, G runs 20 to 24, H moves to day 25 and the project finishes on day 28, five days late. The 8 days of float on network cabling are unaffected, so the cabling contractor does not need to be rebooked.

The team now looks at its discretionary links. If IT set-up can start on temporary desks as soon as cabling is finished (removing the SS link from E), F runs 8 to 12 and is no longer critical. The move is then driven by packing (finishing on day 24) and the project ends on day 27, recovering one day. This is the kind of what-if analysis that is only possible when dependencies are recorded properly.

Step 4: see what the link types saved

If every link had been finish-to-start, IT set-up would have waited for furniture installation to finish (day 18), finishing on day 22, and the project would have ended on day 25. Using SS+1 for IT set-up and SS for packing saves 2 days on the original plan, at the cost of some overlap risk that the team has accepted.

Tip

When you present a schedule, point out the external dependencies on or near the critical path. They are where a phone call today can save a week later.

Showing task dependencies on a Gantt chart and network diagram

On a Gantt chart a dependency is drawn as an arrow from the predecessor bar to the successor bar. The end of the bar the arrow leaves and the end it enters show the type: from the right end to the left end is FS, left to left is SS, right to right is FF. Most tools also let you highlight the critical path in red and show the driving predecessor of a selected task.

A project network diagram shows the same logic without the timescale. Activities are boxes and dependencies are arrows. It is the better view for checking the logic itself: open ends, loops and missing hand-offs are easy to see, while on a busy Gantt chart they are hidden among the bars.

Most project management tools draw dependencies for you once you enter predecessors. Wrike includes interactive Gantt charts with dependencies, critical path and baselines on paid plans, and Smartsheet combines a spreadsheet grid with dependencies, Gantt view and critical path.

How to manage task dependencies

Identifying dependencies is half the job. Keeping them under control through delivery is the other half.

  1. Let the logic drive the dates. Avoid typing start dates into a scheduling tool, because a fixed date overrides the dependencies and the schedule stops reacting to delays. Use a date constraint only for a genuine external date, and record why.
  2. Name an owner for every external dependency. The owner keeps in touch with the supplier, regulator or other team and reports any change early.
  3. Track external dependencies as milestones. "Planning permission granted" or "API available in test" as a milestone makes them visible on the timeline and easy to report.
  4. Review dependencies at every status meeting. Go through those due in the next two to four weeks and confirm each is still on track. Log them in a RAID log so nothing is forgotten.
  5. Watch merge points. An activity with several predecessors (like move day in the example) starts only when the last of them finishes. These are frequent points of delay; consider a small buffer before them.
  6. Protect the critical path. Put your best people, earliest confirmations and closest monitoring on critical and near-critical dependencies.
  7. Use discretionary links deliberately. If the schedule needs to come in, review soft logic first, then consider other schedule compression options.
  8. Re-check the logic after changes. Every approved change request can add, remove or alter dependencies. Re-run the network check before re-baselining the schedule; see project baseline.

Task dependencies in Agile projects

Agile teams use the same idea with different tools. Inside a sprint, the team manages dependencies informally: it orders the sprint backlog so that items others depend on come first, and it swarms on blocked items. Between teams and with the outside world, dependencies need more structure.

  • Link backlog items. Most Agile tools support links such as "blocks" and "is blocked by" between work items, so a blocked story is visible on the board.
  • Raise dependencies in refinement. When a story needs something from another team, raise it before sprint planning, not during the sprint.
  • Plan dependencies across teams. In SAFe, teams map cross-team dependencies on the ART planning board (formerly the program board) during PI planning, drawing a red string from the team that provides a dependency to the feature that needs it. Smaller set-ups use a Scrum of Scrums to coordinate.
  • Design dependencies out. Cross-functional teams that can deliver a feature end to end have fewer hand-offs. Reducing dependencies is usually more effective than managing them.

On Agile projects with fixed external dates, a high-level timeline that shows epics and external milestones can help.

Common task dependency mistakes

MistakeWhy it hurtsFix
Open ends (activities with no predecessor or no successor)A delay to that activity does not move anything, so the end date looks safer than it isLink every activity into the network except the start and finish milestones
Hard-coded start datesThe schedule stops reacting to delays and the critical path breaksLet dependencies set dates; use constraints only for real external dates
Redundant links (A to C when A to B to C already exists)Clutters the diagram and makes changes harderLink only to immediate predecessors
Lags used instead of activitiesHidden work has no owner and is not trackedMake any work in the gap a real activity
Circular logic (A needs B, B needs A)The schedule cannot be calculatedSplit one activity into two parts or rethink the sequence
Overusing start-to-finishConfusing to read and easy to get backwardsRewrite as FS where possible
Linking summary tasksHides which detailed activity actually drives the dateLink detailed activities and milestones, not summary rows
Missing external dependenciesThe plan looks optimistic until the supplier or approver is lateRun a specific check for suppliers, approvals and other projects
Treating every link as mandatoryNo room to recover when the schedule slipsLabel discretionary links so you know what can be changed

Frequently asked questions

What is a task dependency?

A task dependency is a logical relationship between two activities that controls when one (the successor) can start or finish relative to the other (the predecessor). Dependencies set the order of work and allow a schedule to calculate dates and the critical path.

What are the four types of task dependencies?

Finish-to-start (the successor cannot start until the predecessor finishes), start-to-start (it cannot start until the predecessor starts), finish-to-finish (it cannot finish until the predecessor finishes) and start-to-finish (it cannot finish until the predecessor starts).

Which type of task dependency is most common?

Finish-to-start. Most links in a typical schedule are FS, and it is the default type when you link tasks in most scheduling tools.

What is an example of a start-to-finish dependency?

A hand-over: the night security shift cannot finish until the day shift has started, or an old system cannot be switched off until the new system goes live. Start-to-finish is the least common type.

What is the difference between mandatory and discretionary dependencies?

A mandatory dependency (hard logic) is required by the nature of the work, the law or a contract, such as foundations before walls. A discretionary dependency (soft logic) is a preferred order based on best practice, and can be changed if you accept more risk.

What is an external dependency?

A dependency on something outside the project team's control, such as a supplier delivery, a regulator's approval, another project's output or a client decision. Give each one an owner and track it as a milestone.

Can a task have more than one dependency?

Yes. An activity can have several predecessors and several successors. When it has several predecessors, the one that finishes latest (the driving predecessor) sets its start date.

What happens when a dependency is delayed?

Every successor moves by the amount of the delay, minus any float it has. If the delayed activity is on the critical path, the project end date moves too, unless you compress the schedule.

How do task dependencies affect the critical path?

The critical path is the longest chain of dependent activities, so it is defined by the dependencies. Adding, removing or changing a link can change which activities are critical and how long the project takes.

What is the difference between a dependency and a constraint?

A dependency links two activities. A constraint is a limit on an activity or the project, such as a fixed date, a budget cap or limited resources. A constraint can override dependency logic, so use date constraints sparingly.

How do I show task dependencies on a Gantt chart?

Enter the predecessors for each task and the tool draws arrows between the bars. The ends of the bars the arrow connects show the type: finish to start, start to start, finish to finish or start to finish.

What does 3FS+2d mean?

It is Microsoft Project notation for a finish-to-start dependency on task 3 with a 2-day lag: the task can start 2 days after task 3 finishes. A bare 3 means finish-to-start with no lag.

What is a dependency matrix?

A grid listing teams or workstreams on both axes, with each cell showing what one needs from the other and by when. It gives an overview of cross-team dependencies on larger programmes.

How do Agile teams manage dependencies?

Within a team, by ordering the backlog and swarming on blocked items. Across teams, by linking work items (blocks / is blocked by), raising dependencies during refinement, mapping them at PI planning or a Scrum of Scrums, and designing teams to need fewer hand-offs.
