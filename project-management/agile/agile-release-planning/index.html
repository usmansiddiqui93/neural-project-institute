Agile Release Planning: How to Plan Releases in Agile

Release planning answers the question every stakeholder asks: "When will we get it?" In Agile, the answer is a forecast built from real data and updated every sprint, rather than a date fixed at the start.

What a release plan is

A release plan groups backlog items into one or more upcoming releases and forecasts when each is likely to be ready. It sits between the long-term product roadmap and the detailed plan for each sprint.

Fixed date or fixed scope?

ApproachWhat is fixedWhat flexesExample
Fixed dateRelease dateScopeA launch at a trade show
Fixed scopeFeature setDateA minimum set needed to replace an old system

Agile teams avoid fixing both date and scope at once. If both are fixed, quality usually suffers.

Steps to build a release plan

  1. Set the release goal. Describe the outcome the release should achieve.
  2. Select and order backlog items that contribute to the goal.
  3. Estimate them with story points or T-shirt sizes.
  4. Check capacity using recent velocity and planned availability.
  5. Forecast a range: optimistic and pessimistic sprint counts.
  6. Identify dependencies and risks with other teams or suppliers.
  7. Agree the plan with stakeholders and publish it.
  8. Update every sprint using actual progress.

Communicating release forecasts

  • Give ranges, not single dates: "between mid-May and early June".
  • Show a release burnup chart so stakeholders can see both progress and scope changes.
  • Separate must-have items from nice-to-have items, so trade-offs are clear.

Release planning at scale

When several teams contribute to one release, they plan together. In SAFe, this happens in PI Planning.

Key takeaways

  • Release plans forecast when a set of backlog items will be ready.
  • Fix either date or scope, not both.
  • Use velocity ranges and update the forecast every sprint.

Frequently asked questions

How far ahead should a release plan go?

Usually one to three releases, or roughly three to six months. Beyond that, a roadmap of outcomes is more useful than a detailed plan.

Who owns the release plan?

The Product Owner or product manager, working closely with the team and stakeholders.
