Agile Software Development: Practices, Process and Examples

Agile software development is a way of building software in small, working increments, with frequent feedback from users and the engineering practices that keep code safe to change. Frameworks such as Scrum and Kanban organise the work; practices from Extreme Programming (XP), such as test-driven development and continuous integration, make it possible to release small changes often without breaking what already works.

Key takeaways

  • Agile software development rests on the 2001 Agile Manifesto, whose principles name working software as "the primary measure of progress" and call for "continuous attention to technical excellence".
  • Scrum does not prescribe engineering practices and Kanban does not either; XP does. Most software teams combine a framework for organising work with XP-style practices for building it.
  • Continuous integration only works when the automated tests are fast. A test suite shaped like a pyramid (many unit tests, few end-to-end tests) can give feedback in minutes; an inverted suite can take hours.
  • Under the 2020 Scrum Guide a team may release several times within a Sprint: the Sprint Review is not a release gate.
  • DORA measures software delivery with five metrics: change lead time, deployment frequency, failed deployment recovery time, change fail rate and deployment rework rate.

What is Agile software development?

Agile software development is an iterative approach to building software in which a small, cross-functional team delivers working increments in short cycles, gets feedback from users and stakeholders, and adapts the plan. It relies on automated testing, frequent integration and continuous refactoring so that the code stays easy and safe to change as requirements evolve.

The term comes from the Agile Manifesto, written in 2001 by a group of software practitioners. Three of its twelve principles describe software delivery directly:

  • "Deliver working software frequently, from a couple of weeks to a couple of months, with a preference to the shorter timescale."
  • "Working software is the primary measure of progress." Documents, designs and percentage-complete estimates are not.
  • "Continuous attention to technical excellence and good design enhances agility." Teams that let code quality slide lose the ability to change direction cheaply.

Agile is a set of values and principles, not a single method. It does not mean working without plans or documentation: Agile teams plan at several levels (product, release, iteration and day) and keep the documentation their users and future maintainers need, such as API references, decision records and readable automated tests. What changes is that plans are revised as the team learns, rather than fixed at the start.

This guide covers the day-to-day engineering side. For the phases a product goes through from concept to retirement, see the Agile development life cycle.

How a change flows from backlog to production

The sequence below is typical for a Scrum team using XP practices. A Kanban team follows the same technical flow without Sprints.

  1. The Product Owner orders the Product Backlog. Items are usually written as user stories with acceptance criteria, and refined until they are small enough to finish in a few days.
  2. The Developers plan the Sprint. They select items towards a Sprint Goal and break them into tasks. Scrum leaves the choice of technique to them.
  3. Acceptance criteria become tests. A criterion such as "Given I request a reset, when I open the link within 1 hour, then I can set a new password" is turned into an automated acceptance test before or while the code is written.
  4. Code is written test-first in small steps, often in pairs, and refactored as it goes.
  5. Each change is merged into the shared main branch at least daily. A continuous integration (CI) server builds the code and runs the automated tests on every merge.
  6. The deployment pipeline promotes the build through further automated checks to a production-like environment, so the software is always in a releasable state.
  7. The change is released when the business decides. Unfinished features can be deployed switched off behind a feature flag and switched on later, which separates deployment (a technical event) from release (a business decision).
  8. The team inspects the result: with stakeholders at the Sprint Review, through usage data in production, and in the Sprint Retrospective.

Step 7 corrects a common misreading of Scrum. The 2020 Scrum Guide states that "multiple Increments may be created within a Sprint" and that "the Sprint Review should never be considered a gate to releasing value". A team can deploy every day and still hold a Sprint Review to inspect progress towards the Product Goal.

Core engineering practices

Several of these practices (test-first programming, pair programming, continuous integration, refactoring and collective ownership) were brought together by Kent Beck in *Extreme Programming Explained* (first edition 1999; second edition with Cynthia Andres, 2004); continuous delivery and the DORA guidance on trunk-based development came later, from the continuous delivery and DevOps movements. The practices depend on one another: refactoring is risky without tests, and continuous integration is impractical when the tests take hours.

Test-driven development

TDD works in a short loop often described as red, green, refactor: write a test that fails because the behaviour does not exist yet, write just enough code to make it pass, then tidy the design while the tests stay green. The tests are a by-product; the main purpose is to drive the design in small, verifiable steps and to leave behind a safety net for later changes.

TDD suits business rules, calculations and code that will change. It is harder to apply to user-interface layout, exploratory prototypes that will be thrown away, and code that wraps external systems, where teams often write tests after a short spike instead. Treat claims that TDD always reduces defects with caution: the benefit depends on the team's skill and on whether the tests check behaviour rather than implementation details.

Continuous integration and trunk-based development

Martin Fowler's article on the practice (updated in January 2024) defines continuous integration as each team member merging their changes into a shared codebase at least daily, with every integration verified by an automated build that includes tests. He notes that Kent Beck developed the practice as part of XP in the 1990s, and that running a CI server against a long-lived feature branch is not continuous integration, because the branch is not merged with everyone else's work.

DORA's guidance on trunk-based development gives measurable thresholds: three or fewer active branches in the repository, branches that last no more than a few hours, merges to trunk at least once a day, and no code freezes or integration phases. Two supporting rules follow. When the main build breaks, fixing it comes before any new work, reverting the faulty commit if it cannot be fixed within a few minutes. And reviews must be quick: DORA recommends reviewing synchronously and tracking how long approvals take, because a review that waits days pushes developers to batch changes, which makes reviews larger and slower still.

Code review and pair programming

Both practices put a second pair of eyes on every change and spread knowledge of the codebase. Pairing does it continuously, while the code is written; review does it afterwards. Many teams pair on risky or unfamiliar work and use lightweight review for the rest. When more than two people work together on one item, the practice is usually called mob or ensemble programming; our guide to Agile swarming explains when concentrating effort on one item helps and when it does not.

Refactoring and simple design

Refactoring changes the internal structure of code without changing what it does, in steps small enough that the tests confirm nothing broke. Combined with XP's preference for the simplest design that meets today's needs, it lets architecture evolve with the product instead of being fixed up front. Where shortcuts are taken deliberately, record them: our guide to technical debt in Scrum explains how to make that debt visible and decide when to pay it down.

Test automation and the test pyramid

Mike Cohn described the test automation pyramid in *Succeeding with Agile* (2009). Its two rules, as summarised by Ham Vocke on martinfowler.com, are to write tests at different levels of granularity and to have fewer tests the higher the level. Unit tests at the base are fast and precise; service or integration tests in the middle check that components work together; a small number of end-to-end tests at the top check complete user journeys through the interface. Fowler describes end-to-end tests as brittle, expensive to write and slow to run, and calls a suite dominated by them an "ice-cream cone".

DORA's test automation guidance sets the practical target: developers should get feedback from automated tests in less than ten minutes, both locally and from the CI system, and flaky tests should not be tolerated because a failure must indicate a real defect. The worked example below shows why the shape of the suite decides whether that target is reachable.

Continuous delivery and feature flags

Continuous delivery extends CI: every change that passes the pipeline is releasable, and releasing is a routine, automated action. Feature flags (also called feature toggles) let a team merge and deploy unfinished work while keeping it switched off. Pete Hodgson's article on martinfowler.com advises that release toggles "should generally not stick around much longer than a week or two", because every flag adds conditional logic and test combinations; old flags become a form of technical debt.

Scrum, XP and Kanban in software teams

Agile software teams rarely use one method in pure form. The frameworks answer different questions, which is why they combine well.

The practical consequence: adopting Scrum alone does not give a team the ability to release working software every Sprint. If the Increment cannot meet the Definition of Done without a manual test phase, the bottleneck is technical, and the fix is in the engineering practices rather than in the Scrum events.

Worked example: test-suite shape and CI feedback time

This example is illustrative. The team, product and test durations are hypothetical assumptions chosen to show the arithmetic; measure your own suite before drawing conclusions.

A team of five developers maintains a customer self-service web portal. Its next story is US-01 from our user story template: "As a customer, I want to reset my password by email so that I can log in without calling support". Each developer merges to main about twice a day, so the CI pipeline runs about 10 times per working day.

Assumed average run time per test: unit test 0.02 seconds; integration test 1.5 seconds; end-to-end browser test 40 seconds.

Step 1: total run time of each suite

Suite run time (s) = Σ (number of tests at a level × average seconds per test at that level), where the sum runs over the unit, integration and end-to-end levels.

LevelIce-cream cone suitePyramid suite
Unit (0.02 s each)300 tests = 6 s2,400 tests = 48 s
Integration (1.5 s each)150 tests = 225 s200 tests = 300 s
End-to-end (40 s each)250 tests = 10,000 s25 tests = 1,000 s
Total, run one after another700 tests = 10,231 s (170.5 min, 2.84 h)2,625 tests = 1,348 s (22.5 min)

The pyramid suite has almost four times as many tests yet runs more than seven times faster. In the cone, end-to-end tests account for 97.7% of the run time.

Step 2: split the pipeline into stages

The pyramid team runs unit and integration tests in a commit stage: 48 + 300 = 348 seconds, or 5.8 minutes, inside DORA's ten-minute target. The 25 end-to-end tests run in a following acceptance stage spread across 4 parallel test runners: 1,000 ÷ 4 = 250 seconds (4.2 minutes). The full pipeline takes 348 + 250 = 598 seconds, just under 10 minutes.

The cone team can also parallelise, but even with 4 runners its end-to-end tests take 10,000 ÷ 4 = 2,500 seconds, so the full run is 6 + 225 + 2,500 = 2,731 seconds (45.5 minutes).

Step 3: daily load on the pipeline

Daily pipeline time = merges per day × run time per merge. For the cone suite run serially: 10 × 2.84 h = 28.4 hours of pipeline time per 8-hour working day. The builds cannot keep up, so in practice the team merges less often, batches changes and stops doing continuous integration. For the pyramid team: 10 × 5.8 minutes = 58 minutes of commit-stage time per day, or about 100 minutes (10 × 598 seconds) including the acceptance stage.

Interpreting the result

The shape of the suite, not its size, decides whether developers can integrate several times a day. For US-01, the pyramid team would cover the token-expiry rule ("within 1 hour") with fast unit tests at the boundaries (59 minutes, 60 minutes, 61 minutes), the email service with an integration test, and the whole journey with one end-to-end test. The cone team would test each boundary through the browser.

What to do with this: if your commit stage takes more than ten minutes, measure time per test level before buying more build capacity. Move checks of business rules down to unit level, delete end-to-end tests that duplicate lower-level ones, and fix or quarantine flaky tests. Plan this work as backlog items with visible capacity, the same way as other technical debt.

Limitations. Real test durations vary widely by technology and environment. Parallel runners cost money and need isolated test data. Fewer end-to-end tests also means some integration faults surface later, so teams usually add monitoring and fast rollback in production. A pyramid is a heuristic, not a rule: some systems, such as thin user interfaces over third-party services, legitimately need a larger middle layer.

A Definition of Done for a software team

The 2020 Scrum Guide defines the Definition of Done as "a formal description of the state of the Increment when it meets the quality measures required for the product". It does not say what those measures are; each team or organisation decides. An illustrative Definition of Done for the portal team above might be:

  • Code merged to main, with the CI build passing.
  • Automated tests added at the lowest useful level; acceptance criteria covered by passing tests.
  • Code reviewed or written in a pair.
  • Static analysis and dependency security scans show no new high-severity findings.
  • Deployed to the staging environment by the pipeline, not by hand.
  • Feature flag in place if the feature is not yet released to users, with a removal date recorded.
  • User-facing help or API documentation updated.

Notice what is absent: "tested by QA in the next Sprint" and "ready for the release candidate". Either would mean the Increment is not actually done. If the team cannot yet meet a full Definition of Done, make the gap explicit and plan work to close it rather than quietly lowering the bar.

Measuring Agile software delivery

Velocity says how much the team estimated it finished; it says nothing about whether software reached users or how reliably. Software teams therefore add delivery, flow, quality and outcome measures.

For delivery, the most widely used set comes from DORA (DevOps Research and Assessment). Its metrics guide, last updated in January 2026, defines five software delivery metrics in two groups:

MetricGroupDORA definition (paraphrased)
Change lead timeThroughputTime for a change to go from committed to version control to deployed in production
Deployment frequencyThroughputNumber of deployments over a period, or time between deployments
Failed deployment recovery timeThroughputTime to recover from a deployment that fails and needs immediate intervention
Change fail rateInstabilityShare of deployments that need immediate intervention after deployment
Deployment rework rateInstabilityShare of deployments that are unplanned and happen because of an incident in production

Lists that show four metrics and include "time to restore service" or "mean time to recover" are out of date: DORA renamed and narrowed that measure in 2023 and added deployment rework rate in 2024. Read the throughput and instability groups together, compare a service with its own history rather than with other teams, and do not turn any single metric into a target.

DORA's metrics start at the commit. Customers experience the whole journey from request to release, so add Kanban flow measures such as cycle time and work item age, quality measures such as escaped defects, and outcome measures such as adoption of the feature.

Agile and DevOps

Agile software development changed how teams plan and build software; DevOps carries the same collaboration, automation and fast feedback into deployment and operations. In an Agile team without DevOps, developers may finish an Increment every two weeks while a separate operations group deploys it quarterly, so users see little of the benefit. DevOps closes that gap with shared ownership of the service in production, infrastructure defined as code, monitoring, and blameless reviews after incidents.

The two overlap heavily: continuous integration and test automation are core practices in both. A useful distinction for project managers is scope. Agile practices govern the work from idea to a releasable Increment; DevOps practices govern the path from commit to a running, observed service, and back again as feedback. Teams that also handle incidents and requests alongside planned work will find practical policies in our guide to Agile IT operations.

AI coding assistants in an Agile team

AI coding assistants generate code, tests and explanations from natural-language prompts and the surrounding code. In an Agile team they are most useful for drafting unit tests from acceptance criteria, explaining unfamiliar legacy code before refactoring, and producing boilerplate. They do not know the product's goals, can produce plausible but wrong code, and may reproduce insecure patterns.

DORA's 2025 report, *State of AI-assisted Software Development*, based on responses from nearly 5,000 technology professionals, concluded that AI acts mainly as an amplifier: it magnifies the strengths of high-performing organisations and the dysfunctions of struggling ones. In practice that points back to the practices above. Generated code still goes through tests, review and the pipeline; large AI-generated changes should be split into small batches that a reviewer can actually check; and the team, not the tool, remains accountable for what reaches production. Agree which assistants may see proprietary code and customer data before anyone uses them.

When Agile software development is harder

The practices apply widely, but some contexts need adaptation rather than direct adoption.

  • Regulated or safety-critical software (medical devices, avionics, payments) may require formal verification and traceability before release. Teams can still integrate continuously and keep the software releasable, while production releases follow the approval regime. Automated tests and pipeline logs often make the required evidence easier to produce, not harder.
  • Legacy systems without tests cannot be refactored safely at first. Start by adding characterisation tests around the code you need to change, and grow coverage where change happens rather than across the whole system.
  • Embedded software tied to hardware has slower feedback because hardware arrives late or in small quantities. Simulators, hardware-in-the-loop rigs and a clear split between hardware-independent and hardware-specific code restore some of the speed.
  • Fixed-price, fixed-scope contracts conflict with welcoming changing requirements. Options include fixing time and budget while flexing scope, or contracting in phases. Our comparison of Agile vs Waterfall explains how to judge which approach a project needs.
  • Many teams on one product need integration across teams, not only within them. Shared trunk, contract tests between services and a common Definition of Done matter more than a scaling framework's ceremonies.

Common mistakes in Agile software development

  • Adopting the events without the engineering. Two-week Sprints with a manual, month-long test phase produce mini-waterfalls. The Increment never meets the Definition of Done in the Sprint.
  • Calling long-lived feature branches CI. A green build on a branch that has not been merged for a week says little about whether the product works.
  • An ice-cream cone test suite. Slow, brittle end-to-end tests make developers wait, re-run failures and eventually ignore red builds.
  • Treating refactoring as a separate project. Debt grows while the "clean-up Sprint" waits for approval. Refactor in small steps as part of each story.
  • Using velocity as a productivity target. Teams inflate estimates; nothing about delivery improves. Use velocity only for the team's own forecasting.
  • Quoting outdated DORA metrics or ranking teams by them. Use the current five, read them together and compare a service with its own history.
  • Leaving feature flags in place for months. Each forgotten flag adds code paths that nobody tests.

What the project manager does in an Agile software team

Scrum has no project manager accountability, and many Agile software teams work without one. Where a project manager is involved, typically across several teams or with external suppliers and governance, the role shifts from assigning tasks to creating the conditions for the practices above to work:

  • Protect capacity for technical work. Test automation, pipeline improvement and debt reduction compete with features; make them visible in the backlog and in Sprint planning so trade-offs are explicit.
  • Plan releases around flow, not dates alone. Forecast with the team's own throughput or velocity and update the forecast every Sprint; see Agile release planning.
  • Replace document gates with automated evidence. Pipeline results, test reports and peer review records can satisfy many governance and audit needs.
  • Report with delivery and outcome measures, not percentage complete: DORA metrics, cycle time and feature adoption tell stakeholders more.
  • Remove cross-team and supplier blockers, such as environment access, slow security approvals or late hardware.

Frequently asked questions

What is Agile software development in simple terms?

Building software in small, working pieces that are tested, integrated and shown to users often, so the team can learn and change direction cheaply. It is based on the values and principles of the 2001 Agile Manifesto.

Is Agile software development the same as Scrum?

No. Agile is a set of values and principles; Scrum is one framework that applies them. Scrum does not prescribe engineering practices, so software teams usually add practices from Extreme Programming such as test-driven development and continuous integration.

What are the most important Agile engineering practices?

Automated testing (often test-first), continuous integration into a shared main branch, refactoring, code review or pair programming, and a deployment pipeline that keeps the software releasable. They support one another, so adopting one without the others gives limited benefit.

How often should code be integrated in Agile?

At least daily. Martin Fowler's definition of continuous integration and DORA's trunk-based development guidance both call for merging to the main branch at least once a day, with branches that live for hours rather than weeks.

Can a Scrum team release before the Sprint Review?

Yes. The 2020 Scrum Guide says multiple Increments may be created within a Sprint and that the Sprint Review should never be considered a gate to releasing value.

What are the DORA metrics for Agile software teams?

Five software delivery metrics: change lead time, deployment frequency and failed deployment recovery time (throughput), plus change fail rate and deployment rework rate (instability). Older lists with four metrics and "time to restore service" are out of date.

Does Agile software development still need documentation?

Yes, enough for users and future developers: clear code, automated tests that describe behaviour, API documentation, decision records and operating instructions. The Manifesto values working software more than comprehensive documentation, not instead of it.

How big should a user story be in Agile software development?

Small enough to be built, tested and integrated in a few days, so several stories finish within a Sprint. Large stories delay feedback and encourage long-lived branches.
