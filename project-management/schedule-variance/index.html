Schedule Variance (SV): Formula, Examples and Analysis

Schedule variance (SV) tells you whether a project has completed more or less work than planned by a given date. It is calculated as SV = EV - PV: a negative result means you are behind schedule, and a positive result means you are ahead. This guide covers the formula, a worked example across five work packages, how to convert SV into time with earned schedule, and what to do when the number turns red.

Key takeaways

  • SV = EV - PV. Negative means less work done than planned; positive means more.
  • SV% = SV / PV x 100 and SPI = EV / PV let you compare work packages and projects of different sizes.
  • SV is measured in money, not time, and drifts back to zero as the project finishes, even if it finishes late.
  • A healthy total SV can hide a slipping critical path, so always check critical activities too.
  • Earned schedule converts SV into time units (SV(t) and SPI(t)) and gives a forecast finish date.

What is schedule variance (SV)?

Schedule variance (SV) is the difference between the budgeted value of the work actually completed (earned value, EV) and the budgeted value of the work planned to be completed (planned value, PV) at a given status date. It shows, in money, how far ahead of or behind plan the work is. A negative SV means the project is behind schedule.

SV is one of the core measures in earned value management (EVM), alongside cost variance, the schedule performance index (SPI) and the cost performance index. Both of its inputs come from the time-phased budget: PV is what the project baseline says should have been earned by now, and EV is what the team has actually earned by completing work.

Older EVM material and some government contracts use different names for the same inputs:

Current termOlder termMeaning
Earned value (EV)BCWP: budgeted cost of work performedThe budget for the work actually done
Planned value (PV)BCWS: budgeted cost of work scheduledThe budget for the work that should have been done by now

So SV = BCWP - BCWS is exactly the same formula as SV = EV - PV.

Tip

Scheduling tools often show a "variance" column comparing baseline dates with current dates, in days. That is useful, but it is not EVM schedule variance. When someone quotes a schedule variance, check whether they mean days of slippage or EV - PV in money.

The schedule variance formula

FormulaWhat it shows
SV = EV - PVSchedule variance in money: the value of work ahead of or behind plan
SV% = (SV / PV) x 100Schedule variance as a percentage of the work planned to date
SPI = EV / PVSchedule performance index: the share of planned work actually achieved
EV = % complete x BACEarned value for a work package or the project

BAC is the budget at completion, the total approved budget for the work, excluding management reserve. PV is read from the cumulative baseline budget at the status date.

A quick example: at the end of month four a project has PV = $80,000 and EV = $70,000.

  • SV = 70,000 - 80,000 = -$10,000.
  • SV% = -10,000 / 80,000 x 100 = -12.5%.
  • SPI = 70,000 / 80,000 = 0.875: the team has achieved 87.5% of the work planned by now.

How to read the result

ResultSPIMeaningTypical response
SV > 0 (positive)Above 1More work done than planned: ahead of scheduleCheck progress is reported accurately and whether the extra work is on the critical path
SV = 0Exactly 1Work done matches the planKeep monitoring
SV < 0 (negative)Below 1Less work done than planned: behind scheduleFind the cause, check the critical path, forecast the finish and agree action

As with cost variance, negative is unfavourable. SV and SPI always point the same way because they use the same inputs. Note the careful wording: "less work done than planned", not "days late". SV measures the value of missing work, which is not the same as how late the project will finish.

How to calculate schedule variance step by step

  1. Fix the status date. EV and PV must relate to the same cut-off, such as the last working day of the month.
  2. Confirm the performance baseline, including approved changes.
  3. Read PV for each work package: the cumulative budget scheduled to be complete by the status date.
  4. Measure progress using agreed rules, such as 0/100 for short tasks, 50/50, or weighted milestones for longer ones.
  5. Calculate EV for each work package (% complete x BAC) and add them up.
  6. Calculate SV, SV% and SPI for each work package and the total.
  7. Compare with the previous period and with your thresholds.
  8. Check whether the work packages behind plan are on the critical path or have float.
  9. Forecast the impact on the finish date and report it.

Steps 2 and 4 cause most errors. A baseline not updated for approved changes makes SV mix performance with scope change. Subjective percent complete (the task stuck at 90% for weeks) inflates EV and makes SV look better than it is.

Worked example: CRM implementation by work package

This is the same illustrative CRM implementation used in our cost variance guide: a budget at completion of $400,000 over a planned ten months. Here is the schedule position at the end of month five.

Work packageBACPVEVSVSV%SPI
1. Requirements and design$60,000$60,000$60,000$00.0%1.00
2. Configuration and build$140,000$98,000$84,000-$14,000-14.3%0.86
3. Data migration$70,000$21,000$28,000+$7,000+33.3%1.33
4. Testing$80,000$26,000$8,000-$18,000-69.2%0.31
5. Training and go-live$50,000$0$0$0--
Project total$400,000$205,000$180,000-$25,000-12.2%0.88

Calculating the totals

  • PV = 60,000 + 98,000 + 21,000 + 26,000 + 0 = $205,000.
  • EV = 60,000 + 84,000 + 28,000 + 8,000 + 0 = $180,000, or 45% of the BAC.
  • SV = 180,000 - 205,000 = -$25,000, and SV% = -25,000 / 205,000 x 100 = -12.2%.
  • SPI = 180,000 / 205,000 = 0.878: the team has completed about 88% of the work planned by now.

What the breakdown tells you

  • Testing is the biggest problem: -$18,000, SPI 0.31. It was planned to start in month four as build modules were handed over, and because build is late it has barely started.
  • Configuration and build is $14,000 behind. This is the root of the testing delay, and the same package drives the cost overrun in the cost variance guide.
  • Data migration is $7,000 ahead, but it has float in this plan. Finishing it early does not bring go-live forward.
  • The total of -$25,000 is therefore flattered by migration. The critical sequence of build, testing and go-live is $32,000 behind.

This is the key lesson: totals net off. Work done early on non-critical packages can hide slippage on the critical path. Look at the breakdown and the critical path before telling a sponsor the project is "only 12% behind".

Tip

Align work packages with your work breakdown structure and schedule, so every SV figure can be traced to activities on the Gantt chart. If you cannot see which activities sit behind a variance, you cannot tell whether it matters.

Cumulative and period schedule variance

Most reports show cumulative SV, from the start of the project to the status date. Period SV looks at one month on its own and shows when a problem started and whether it is getting worse.

MonthPV this monthEV this monthPeriod SVCumulative PVCumulative EVCumulative SVSV%SPI
1$20,000$20,000$0$20,000$20,000$00.0%1.00
2$30,000$25,000-$5,000$50,000$45,000-$5,000-10.0%0.90
3$45,000$40,000-$5,000$95,000$85,000-$10,000-10.5%0.89
4$55,000$45,000-$10,000$150,000$130,000-$20,000-13.3%0.87
5$55,000$50,000-$5,000$205,000$180,000-$25,000-12.2%0.88

Cumulative SV has grown every month since month two, but the period figures add detail. Month four was the worst, when build slipped and testing could not start. In month five the team earned 91% of what was planned for the month (50,000 / 55,000), against 82% in month four, and cumulative SPI ticked up from 0.87 to 0.88.

That is what early recovery looks like: period performance better than the cumulative figure, even though cumulative SV is still negative. If the period figures get worse again, the problem is structural and the forecast should change.

Plot cumulative PV, EV and AC on one chart: the gap between PV and EV is your schedule variance, and the gap between EV and AC is your cost variance. See our guide to the S-curve.

Schedule variance vs SPI and cost variance

MeasureFormulaUnitsBest for
Schedule variance (SV)EV - PVMoney, to dateValue of work ahead of or behind plan
Schedule performance index (SPI)EV / PVRatioEfficiency trend; comparing projects; forecasting
Cost variance (CV)EV - ACMoney, to dateWhether completed work cost more or less than budgeted
Cost performance index (CPI)EV / ACRatioCost efficiency; estimate at completion
SV(t), earned scheduleES - ATTimeHow far behind in time; forecast finish

SV shows the amount of work at stake in money, which matters to a sponsor. SPI shows efficiency as a ratio, which travels well between projects of different sizes. Report both.

SV compares work done with work planned; CV compares work done with what it cost. Both anchor on EV, which is what separates "are we on time?" from "are we spending efficiently?".

Reading schedule variance with cost variance

SVCVWhat it usually meansQuestions to ask
PositivePositiveAhead of schedule and under budgetIs progress reported accurately? Was the plan too cautious?
PositiveNegativeAhead of schedule but over budgetAre we paying for speed with overtime or extra staff? Was that agreed?
NegativePositiveBehind schedule but under budgetAre resources missing? Is work being delayed rather than done cheaply?
NegativeNegativeBehind schedule and over budgetWhat is the root cause? Is a re-plan or change request needed?

The CRM project is in the bottom row: SV -$25,000 and CV -$17,000. That is the hardest combination, because catching up on time usually costs money. The combined forecast AC + (BAC - EV) / (CPI x SPI) captures the effect; see our guide to the estimate at completion.

The limitations of schedule variance

  • It is measured in money, not time. An SV of -$25,000 does not tell you how many days late you are. Earned schedule (below) converts it properly.
  • It returns to zero at the end. When all work is complete, EV = PV = BAC, so SV = 0 and SPI = 1, even if the project finished months late. In the later stages SV gradually loses its power to show schedule problems.
  • It ignores the critical path. EV adds up all work equally, so progress on non-critical work can mask critical delays.
  • It depends on progress measurement. Subjective percent complete inflates EV; front-loaded credit rules flatter SV early.
  • It depends on the baseline. An unrealistic or out-of-date baseline means every variance is measured against the wrong yardstick.
  • It dilutes with level-of-effort work. For activities such as project management, EV is usually set equal to PV, so they always show zero SV.

None of this makes SV useless. It is an early, objective signal that the project is earning value more slowly than planned. It just needs to be read with the schedule, not instead of it.

Tip

Use SV and SPI to ask "are we doing the planned amount of work?" and the critical path and float to ask "will we finish on time?". You need both answers.

Earned schedule: schedule variance in time units

Earned schedule (ES) extends earned value management to measure schedule performance in time rather than money. It was introduced by Walt Lipke in 2003 in the article "Schedule Is Different", published in The Measurable News of PMI's College of Performance Management, and it uses the same PV and EV data you already have.

The idea: find the point at which the current EV should have been earned according to the baseline. If you have earned what the plan expected by month 4.5, but it is now month 5, you are half a month behind.

MeasureFormulaMeaning
Earned schedule (ES)C + (EV - PV at C) / (PV at C+1 - PV at C)When the current EV was planned to be earned. C is the last whole period in which cumulative PV was at or below EV.
Actual time (AT)Periods elapsedHow long the project has been running
SV(t)ES - ATSchedule variance in time; negative means behind
SPI(t)ES / ATTime-based schedule performance index
IEAC(t)Planned duration / SPI(t)Forecast total duration if current performance continues

Worked earned schedule example

In the CRM project, EV at month five is $180,000. Cumulative PV was $150,000 at month four and $205,000 at month five.

  1. Find C: PV at month 4 ($150,000) is below EV and PV at month 5 ($205,000) is above, so C = 4.
  2. ES = 4 + (180,000 - 150,000) / (205,000 - 150,000) = 4 + 0.55 = 4.55 months.
  3. AT = 5 months, so SV(t) = 4.55 - 5 = -0.45 months, roughly two working weeks behind.
  4. SPI(t) = 4.55 / 5 = 0.91.
  5. IEAC(t) = 10 / 0.91 = about 11.0 months: roughly one month late if current performance continues.

That is a far more useful message for a sponsor than "SV is -$25,000".

Why earned schedule matters at the end of a project

Suppose the CRM project finishes all its work at the end of month 12, two months late. At that point EV = PV = BAC = $400,000.

MeasureCalculationResultWhat it says
SV400,000 - 400,000$0On schedule
SPI400,000 / 400,0001.00On schedule
SV(t)ES 10 - AT 12-2 monthsTwo months late
SPI(t)10 / 120.8383% of planned schedule efficiency

Only the time-based measures tell the truth at completion. Earned schedule still adds up all work regardless of the critical path, so use it alongside your schedule.

Schedule variance thresholds and when to act

Most organisations set variance thresholds in the project management plan: limits beyond which the project manager must explain the variance, forecast its impact and propose action. Thresholds often tighten as the project matures, because there is less time to recover.

There is no universal standard. The right limits depend on the industry, the contract and how firm the deadline is. This table is an example to adapt, not a rule:

StatusExample threshold (cumulative)Action
GreenSV% within plus or minus 5%, and no critical milestone forecast lateReport as normal
AmberSV% between -5% and -10%, or a critical milestone up to two weeks lateVariance explanation and recovery plan in the next report
RedSV% beyond -10%, or a critical milestone more than two weeks lateEscalate to the sponsor; re-forecast the finish; consider compression or a change request

Combining SV% with a time check on critical milestones avoids flagging small packages that do not matter while missing critical ones that do. Under these example thresholds the CRM project (-12.2%, forecast about a month late) is red. Many teams also set a favourable threshold, such as +10%, because a large positive variance often signals overstated progress.

Common causes of negative schedule variance

  • Optimistic estimates: best-case productivity, missing tasks or no allowance for risk.
  • Resource shortages: people not available when planned, or shared specialists pulled onto other work.
  • Late inputs: data, approvals, equipment or deliverables from another team, supplier or client.
  • Rework: defects, unclear requirements or design changes.
  • Unapproved scope: scope creep absorbs effort without changing the baseline.
  • Realised risks: supplier failure, outages, regulatory change, weather or site conditions.

When a positive schedule variance is a warning

  • Overstated progress, which inflates EV.
  • Easy, non-critical work done first while harder critical work waits.
  • Work started out of sequence that may need redoing.
  • A cautious baseline with padded durations.

To find the real cause of a significant variance, use a structured technique such as a fishbone diagram or five whys with the people doing the work.

How to fix a negative schedule variance

  1. Validate the data: status date, progress measurement and baseline.
  2. Locate the variance by drilling down to work packages and activities.
  3. Check the critical path. If the late work has enough float, monitor it; if it is critical, act.
  4. Find the root cause: resources, dependencies, rework, scope or estimates.
  5. Forecast the new finish date with SV(t) and SPI(t) or an updated schedule.
  6. Compare recovery options by cost and risk, and agree them with the sponsor.
  7. Raise a change request through change control if the baseline is no longer achievable.
  8. Watch next period's SV and SPI to check the actions are working.

Recovery options

OptionWhen it helpsWatch out for
Remove blockers (decisions, access, inputs)Delays caused by waiting rather than effortNeeds sponsor support
Re-sequence or reassign workPeople on tasks with float can move to critical workSkills match and new overloads; see resource levelling
Fast trackingDependencies are discretionary and requirements stableRework from overlapping work
CrashingMoney is available and extra resources genuinely speed the workExtra cost; new people are slower at first

Example schedule variance explanation

A good explanation states the variance, where it sits, the cause, the impact, the actions and any decision needed. For the CRM project: "The project is $25,000 behind plan (SV% -12.2%, SPI 0.88), about two weeks in time terms. The critical sequence of build and testing is $32,000 behind; data migration is ahead but has float. Build is late because two integration developers joined five weeks after plan. At current performance, go-live moves from the end of month 10 to around the end of month 11. Actions: move one migration analyst to test preparation (PM, from 10 November); overlap testing with the last build sprint for low-risk modules (test lead, plan by 14 November). Decision needed: approve two weeks of contractor support for build, or accept a revised go-live date."

Schedule variance in Agile projects

EVM was designed for plan-driven projects, but schedule variance can be adapted to Agile delivery at release level:

  • Use the release budget as BAC and the story points planned for the release as the scope.
  • PV is the share of points the release plan expected to be done by now, multiplied by BAC.
  • EV is the share of points actually done (meeting the definition of done), multiplied by BAC.
  • Re-baseline planned points when the product owner changes scope, so SV reflects pace rather than scope change.

Illustrative example: a 300-point release has a budget of $300,000 over 12 sprints. After sprint 6 the plan expected 150 points; the team has completed 120. PV = $150,000, EV = $120,000, SV = -$30,000 and SPI = 0.80: the team is delivering about 80% of the planned pace, which a release burn-up chart would also show.

Most Agile teams track this signal directly through burn-ups and velocity, and adjust scope rather than date. Release-level SV is most useful when a PMO needs Agile and predictive projects reported in the same terms. See our guide to Agile metrics and KPIs.

Common schedule variance mistakes

  • Treating SV as a number of days.
  • Reporting only the project total, so non-critical work hides critical slippage.
  • Using subjective percent complete, which inflates EV.
  • Measuring against a baseline that excludes approved changes.
  • Mixing status dates for progress and planned value.
  • Relying on SV and SPI late in the project, when they drift towards zero and one.
  • Explaining the variance without forecasting the finish date.

Frequently asked questions

What is the schedule variance formula?

SV = EV - PV, where EV is earned value (the budget for the work actually completed) and PV is planned value (the budget for the work scheduled to be done by now). As a percentage, SV% = SV / PV x 100.

What does a negative schedule variance mean?

Less work has been completed than planned by the status date, so the project is behind schedule in earned value terms. Check the critical path to see whether the finish date is actually at risk.

Is a positive schedule variance always good?

No. It can come from overstated progress, easy non-critical work done early, or a cautious baseline, and it can hide a slipping critical path.

How do you calculate schedule variance percentage?

Divide SV by PV and multiply by 100. An SV of -$25,000 on PV of $205,000 is -12.2%.

What is the difference between schedule variance and SPI?

Both use EV and PV. SV is the difference in money; SPI is the ratio EV / PV. A negative SV always means an SPI below 1.

What is the difference between schedule variance and cost variance?

Schedule variance (EV - PV) compares work done with work planned. Cost variance (EV - AC) compares work done with what it cost. Both use earned value as the anchor.

Why is schedule variance measured in money?

Earned value measures progress in budget units so that different kinds of work can be added together. Earned schedule converts the result into time.

Why does schedule variance return to zero at the end of a project?

When all work is complete, EV and PV both equal the budget at completion, so SV is zero however late the project finished. Earned schedule's SV(t) does not have this problem.

What is earned schedule?

An extension of earned value management, introduced by Walt Lipke in 2003, that finds when the current EV was planned to be earned. It gives SV(t) = ES - AT and SPI(t) = ES / AT in time units.

What is an acceptable schedule variance?

There is no universal figure. Thresholds are set in the project management plan, often as a percentage band such as plus or minus 5% or 10%, combined with a check on critical milestone dates.

How often should you calculate schedule variance?

At every reporting period: usually monthly on larger projects and weekly or fortnightly on short ones. Use one status date for all figures and track the trend.

Can a project have a positive schedule variance and still be late?

Yes. If non-critical work is ahead while critical-path work slips, total SV can be positive while the finish date moves out.
