Work Package in Project Management: Examples & How-To

A work package in project management is the lowest level of the work breakdown structure (WBS): a defined piece of work, with a clear output, that is small enough to estimate reliably, assign to one owner and track to completion. Work packages are where scope turns into estimates, budgets, schedules and accountability. This guide explains what to include, how to size and create work packages, how they differ from tasks and activities, and walks through a complete worked example.

Key takeaways

  • A work package is the lowest level of the WBS, where cost and duration are estimated and managed.
  • It describes an output (a noun, such as "quote request form"); the activities and tasks inside it describe the work (verbs).
  • Every work package needs one owner, a clear deliverable, acceptance criteria, estimates, dates and dependencies.
  • Use the 8/80 rule and the reporting-period rule as guides to size, not as fixed standards.
  • Work packages roll up into control accounts and the project budget, and break down into schedule activities.
  • In PRINCE2, a work package is also the formal instruction the project manager gives a team manager to deliver specific products.

What is a work package in project management?

A work package is the work defined at the lowest level of a work breakdown structure, for which cost and duration are estimated and managed. It produces a specific, verifiable output, has a single accountable owner and is small enough to plan and control, yet large enough to be worth tracking as a unit.

Think of a work package as a small, self-contained project inside your project. It has its own scope (what it delivers), its own estimates (effort, duration and cost), its own owner and its own definition of done. Once it is approved, the owner and their team can get on with the work, and the project manager tracks it as one line in the plan.

Work packages matter because almost everything in project control is built on them:

  • Estimating. Bottom-up estimates are made at work package level and added up to the project total.
  • Scheduling. Each work package is broken into activities, which are sequenced and scheduled.
  • Budgeting. Work package costs roll up into control accounts and the project budget.
  • Accountability. Each package has one named owner, which removes doubt about who is responsible.
  • Progress tracking. Status, percent complete and earned value are measured package by package.

Where work packages sit in the WBS

A work breakdown structure breaks the total project scope into progressively smaller deliverables. The bottom of each branch is a work package. Under the 100% rule, the work packages together must cover all of the project's scope, including project management work, and nothing outside it.

LevelWhat it representsExample (website project)
1. ProjectThe total scopeNew customer website
2. Major deliverableA main output or phase5 Build
3. Control account (optional)A management point where scope, budget and schedule are integrated and reported5 Build, owned by the development lead
4. Work packageThe lowest WBS element, estimated, owned and tracked5.3 Quote request form
Below the WBS: activitiesScheduled work needed to produce the work packageBuild CRM integration
Below the WBS: tasksSmaller personal steps inside an activityMap form fields to CRM fields

Each work package has a WBS code (such as 5.3) that ties it to its parent and appears in the schedule, budget, timesheets and reports. The detail for each package is recorded in the WBS dictionary, which is essentially a collection of work package descriptions.

Control accounts and planning packages

On larger projects, particularly those using earned value, work packages are grouped under control accounts. A control account is a management point, usually owned by a control account manager, where scope, budget, actual cost and schedule are integrated and compared. Each work package belongs to exactly one control account.

A planning package is a placeholder below a control account for work whose scope is known but not yet detailed. It has a budget but no detailed activities. As the work gets closer, the planning package is converted into one or more work packages. This is the essence of rolling wave planning: plan the near term in detail and the far term at a higher level.

Work package vs task, activity and deliverable

These terms are often used loosely, and project management tools call almost everything a "task". The distinctions are still useful, especially for planning and exams.

TermWhat it isNamed asTypical sizeExample
DeliverableA product, result or capability the project must produceNounWeeks to monthsWebsite build
Work packageThe lowest WBS element, with an owner, estimates and acceptance criteriaNounRoughly 8 to 80 hours of effortQuote request form
ActivityA scheduled piece of work needed to complete a work packageVerb + nounHours to daysBuild CRM integration
TaskA smaller step within an activity, often personalVerb + nounMinutes to hoursTest field validation in Safari
MilestoneA significant point or event with zero durationEventZero durationForm approved for launch

The simplest rule: work packages describe what is produced; activities and tasks describe how it is produced. If a WBS element starts with a verb ("design", "build", "test"), it is probably an activity that belongs inside a work package. For more on the lower levels, see our guide to project tasks and activities.

A work package is not always the same as a deliverable either. A large deliverable may be split into several work packages, while a small deliverable may be a single work package. See our guide to project deliverables.

What a work package includes

A work package description (also called a work package statement or WBS dictionary entry) records everything someone needs to understand, estimate, deliver and accept the work. Scale it to the project: a small internal project may need only the first eight fields; a contract or earned value project will need all of them.

FieldWhat to writeWhy it matters
ID and nameWBS code and a short noun phraseLinks the package to the WBS, schedule and budget
Description and scopeWhat is included and, just as important, what is excludedPrevents gaps, overlaps and scope creep
DeliverableThe specific outputMakes completion visible
Acceptance criteriaMeasurable conditions for "done" and who acceptsAvoids arguments at the end
OwnerOne named personSingle point of accountability
ResourcesPeople, roles, equipment and materialsFeeds resource planning and costing
Effort and durationHours of work and elapsed timeEffort drives cost; duration drives the schedule
Cost estimateLabour, materials and other costsRolls up to the control account and budget
Start and finish datesPlanned dates from the scheduleSets expectations and supports tracking
DependenciesPredecessors, successors and external inputsFeeds the network diagram and critical path
Assumptions and constraintsWhat the estimate depends onExplains variances later
RisksKey risks specific to this packageFeeds the risk register
Progress method and reportingHow progress is measured and how often it is reportedConsistent status and earned value
ApprovalWho approved the package and whenShows that the work is authorised

You do not need to build this from scratch. Our free work package template includes these fields, and the WBS template holds the structure the packages sit in.

How big should a work package be?

There is no formal standard for work package size. The right size is the one that lets you estimate accurately, assign clearly and see progress early, without creating more administration than the work is worth. Four rules of thumb help.

Rule of thumbWhat it saysWhy
8/80 ruleBetween about 8 and 80 hours of effortSmaller packages add overhead; larger ones are hard to estimate and hide problems
Reporting-period ruleNo longer than one or two reporting periodsProblems show up in the next status report, not months later
Single-owner ruleOne person can be accountable for itIf two managers own it, it is probably two work packages
Measurable-output ruleCompletion can be verified objectively"Done" should not be a matter of opinion

Treat these as guides, not laws. The 8/80 rule comes from practitioner experience rather than from a standards body, and large engineering or construction projects often have much bigger packages that are still well controlled. The real test is: can you estimate it, assign it and track it? If yes, stop decomposing.

Signs a work package is too bigSigns a work package is too small
Estimates vary wildly between estimatorsThere are hundreds of packages to track
It spans several months or several teamsReporting takes longer than the work
Status stays at "in progress" for many periodsPackages are really individual tasks
It has several unrelated outputsThe WBS has been decomposed to the level of to-do lists

How to create work packages step by step

  1. Start from an agreed scope. Work from an approved scope statement and requirements. Work packages cannot be better than the project scope they come from.
  2. Decompose the deliverables. Break each major deliverable into smaller components until each branch reaches a piece of work that passes the sizing tests above. Name each element as a noun.
  3. Check the 100% rule. Confirm the children of every element add up to all of its work, with no gaps or overlaps. Include project management, testing, training and handover packages.
  4. Assign an owner to each package. Choose the person who will be accountable for delivery, and agree it with them and their line manager. A RACI matrix helps where several roles are involved.
  5. Write the work package description. Fill in the fields from the table above, starting with the description, exclusions, deliverable and acceptance criteria.
  6. Estimate with the people doing the work. Ask the owner and team to estimate effort, duration and cost. Bottom-up effort estimation at this level is usually the most accurate method. Our project cost estimate template turns effort into cost.
  7. Identify activities and dependencies. Break each package into activities, link them with dependencies and feed them into the project schedule.
  8. Review and approve. Review packages with owners and the sponsor, resolve gaps, then include them in the scope, schedule and cost baselines.
  9. Authorise and track. Release each package when it is due to start, then track progress, cost and issues against its baseline.
Tip

Write the exclusions as carefully as the inclusions. "Excludes content writing and translation" in a build work package prevents one of the most common arguments at acceptance.

Work package example: a website build

This example is illustrative: the project, rates and figures are invented to show how one work package is defined, broken down and rolled up.

A company is replacing its customer website. The WBS has six major deliverables: 1 Project management, 2 Discovery, 3 Design, 4 Content, 5 Build and 6 Launch. The development lead owns deliverable 5 Build, which is managed as a control account and broken into four work packages.

Step 1: decompose the deliverable

WBS codeWork packageOwnerEffortCost
5.1Page templatesFront-end developer72 hours£4,680
5.2CMS configurationBack-end developer40 hours£2,600
5.3Quote request formBack-end developer56 hours£3,430
5.4Analytics and trackingFront-end developer20 hours£1,300
5 Build (control account)Development lead188 hours£12,010

Every package sits within the 8/80 range, each has one owner, and the four packages together cover all of the build work. Content writing is in deliverable 4, so it is excluded here.

Step 2: write the work package description

Field5.3 Quote request form
DescriptionAn online form on the Contact and Product pages that lets visitors request a quote and sends each request to the CRM
ExcludesForm copy (supplied by 4 Content), CRM licence changes, email nurture sequences
DeliverableWorking form in the live environment, connected to the CRM
Acceptance criteriaSubmissions create a CRM lead within 1 minute; required-field validation works; form meets the agreed accessibility standard; spam protection blocks automated test submissions; accepted by the sales operations manager
OwnerBack-end developer
ResourcesBusiness analyst 6 h, back-end developer 40 h, tester 10 h, CRM sandbox account
Effort and duration56 hours over 10 working days
Cost£3,430 (analyst at £55/h, developer at £65/h, tester at £50/h)
DependenciesStarts after 3.2 Form design is approved and 5.2 CMS configuration is complete; 6.1 Launch testing depends on it
AssumptionsCRM API access is available by day 1; field list does not change after activity A1
RisksCRM API rate limits; late changes to form fields from sales
Progress methodWeighted milestones: fields agreed 10%, form built 40%, integration working 70%, tested 90%, accepted 100%

Step 3: break the work package into activities

IDActivityRoleEffortPredecessor
A1Confirm form fields and validation rulesBusiness analyst6 hNone
A2Build front-end formDeveloper16 hA1
A3Build CRM integrationDeveloper14 hA1
A4Add spam protection and accessibility fixesDeveloper6 hA2
A5Test form, integration and accessibilityTester10 hA3, A4
A6Fix defects and obtain acceptanceDeveloper4 hA5

The activities add up to 56 hours: 6 for the analyst, 40 for the developer and 10 for the tester. The cost works out as 6 × £55 + 40 × £65 + 10 × £50 = £330 + £2,600 + £500 = £3,430. These activities, not the work package itself, go into the Gantt chart with their dependencies.

Step 4: track progress

At the end of week one, A1 and A2 are complete and A3 is half done. Under the weighted milestone rule, the package has reached "fields agreed" and "form built", so it is reported as 40% complete, giving an earned value of 40% × £3,430 = £1,372. If actual cost to date is £1,600, the package is slightly over budget for the work done, which the owner explains in the weekly project status report.

Work packages in PRINCE2

In PRINCE2, the term has a slightly different, more formal meaning. A PRINCE2 work package is a set of information and instructions that the project manager uses to hand over responsibility for delivering one or more products to a team manager or team member. It is both a description of the work and an authorisation to do it.

The project manager authorises work packages as part of controlling a stage. The team manager accepts, executes and delivers them in the managing product delivery process, then reports progress through checkpoint reports. A PRINCE2 work package typically contains:

  • A description of the work and the products to be delivered, with their product descriptions
  • Techniques, processes or standards to be used
  • Agreed tolerances, such as time, cost and scope
  • Constraints, interfaces and dependencies
  • Reporting arrangements, such as how often checkpoint reports are produced
  • Quality requirements and who carries out quality checks
  • The date it was agreed between the project manager and team manager

The two meanings fit together well: a PRINCE2 work package can cover one or several WBS work packages, and in both cases the point is clear, agreed, controllable chunks of work with a named person accountable for delivery.

Tracking work packages and earned value

Because each work package has its own budget and dates, it is the natural unit for measuring progress. The key is to agree, before work starts, how progress will be credited, so that "percent complete" means something.

Progress methodHow it worksBest for
0/100No credit until the package is finishedVery short packages, under one reporting period
50/5050% credit at start, 50% at finishPackages spanning about two reporting periods
Weighted milestonesCredit at defined, verifiable pointsLonger packages with clear intermediate outputs
Units completeCredit by quantity delivered (metres laid, pages built)Repetitive work with countable outputs
Physical percent completeOwner's assessment against defined criteriaWork without natural milestones; needs clear rules

Rolled up to control accounts, these figures give planned value, earned value and actual cost for the whole project. See our guide to earned value management for the formulas and how to read the results.

Benefits of work packages

  • More accurate estimates. Small, well-defined pieces of work are easier to estimate than whole deliverables, and errors partly cancel out when added up.
  • Clear accountability. One owner per package means nobody has to ask who is responsible.
  • Easier delegation. A good description lets the owner and team work with little supervision.
  • Earlier warning of problems. Packages that fit a reporting period show slippage within weeks.
  • Better cost control. Actual costs can be collected and compared package by package.
  • Stronger scope control. Inclusions and exclusions make it obvious when a request is new scope.
  • Reuse. Well-written packages become templates for similar future projects.

MistakeConsequenceFix

No acceptance criteriaDisputes over whether the work is doneWrite measurable criteria and name who accepts
Estimating without the teamOptimistic, unowned estimatesHave the people doing the work estimate it

Packages far too largeProblems hide until lateSplit by output, phase or location to fit a reporting period

Managing work packages in project management software

Most tools do not have a field called "work package", but they all let you represent one. The usual pattern is to make each work package a parent item with its own owner, dates and custom fields, and to add the activities as child tasks.

  • Wrike, our top-rated tool, maps well to a formal WBS: deliverables as projects or folders, work packages as parent tasks with custom fields for WBS code, budget and acceptance criteria, and activities as subtasks on an interactive Gantt chart with dependencies and baselines.
  • monday.com works well when each work package is a group or an item, with subitems for activities and columns for owner, timeline, budget and status.
  • Asana can represent work packages as sections or parent tasks within a project, with subtasks, dependencies and custom fields.
  • ClickUp lets you use lists or parent tasks for work packages, with subtasks, custom fields and Gantt views.
  • Smartsheet uses indented parent rows, so a WBS with work packages and activities looks much like the spreadsheet many planners already use.

Whatever the tool, keep the WBS code in a field so that schedule, cost and status reports can be grouped by work package.

Frequently asked questions

What is a work package in simple terms?

A small, clearly defined chunk of project work with one owner, a specific output, estimates and acceptance criteria. It is the lowest level of the work breakdown structure.

What is an example of a work package?

"Quote request form" on a website project, "electrical first fix" on an office fit-out or "press kit" on a product launch. Each produces a defined output that can be estimated, owned and accepted.

What is the difference between a work package and a task?

A work package describes an output at the lowest level of the WBS. Tasks and activities are the steps needed to produce it. One work package usually contains several activities, and each activity may contain several tasks.

What is the difference between a work package and an activity?

Work packages belong to the WBS and are named as nouns; activities belong to the schedule and are named as verbs. Activities are created by breaking down work packages.

What is the 8/80 rule?

A rule of thumb that a work package should take between about 8 and 80 hours of effort. It is a guide to the right level of detail, not a formal standard.

Who is responsible for a work package?

One named owner is accountable for delivering it, even if several people do the work. On larger projects, the owner reports to a control account manager or the project manager.

What should a work package include?

At minimum an ID, name, description and exclusions, deliverable, acceptance criteria, owner, resources, effort, duration, cost, dates and dependencies. Larger projects add assumptions, risks, progress method and approval.

What is a control account?

A management point in the WBS where scope, budget, actual cost and schedule are integrated and compared for earned value. Each control account contains one or more work packages, and each work package belongs to exactly one control account.

What is the difference between a planning package and a work package?

A planning package is a budgeted placeholder for future work whose scope is known but not yet detailed. It is converted into work packages, with activities and estimates, as the work gets closer.

What is a work package in PRINCE2?

A set of information and instructions that the project manager uses to authorise a team manager or team member to deliver one or more products, including tolerances, quality requirements and reporting arrangements.

How many work packages should a project have?

As many as needed to cover 100% of the scope at a level you can estimate, assign and track. A small project might have 10 to 20; a large programme can have hundreds.

Is a work package the same as a deliverable?

Not always. A work package always produces an output, but a large deliverable may be split into several work packages, and some outputs, such as a test report, exist mainly to support other deliverables.

What is the difference between a work package and a WBS dictionary?

The work package is the piece of work itself. The WBS dictionary is the document that describes every WBS element, including each work package's scope, owner, estimates and acceptance criteria.
