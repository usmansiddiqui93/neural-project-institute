IT 运维中的敏捷：运维团队如何应用敏捷和 DevOps

IT 运维中的敏捷是指将敏捷的价值观和实践（如工作可视化、短反馈循环和持续改进）应用于负责运行基础设施、网络、服务台和生产系统的团队。由于运维工作混合了计划内项目和计划外事件，运维团队通常青睐 Kanban，并通过 DevOps 与开发团队紧密协作。

要点总结

  • 运维团队通过让所有工作可视化并为中断做好规划来应用敏捷。
  • 带有服务类别和 WIP 限制的 Kanban 通常比严格的冲刺更适合运维。
  • 为计划外工作预留产能，并持续投入自动化。
  • 通过 DevOps 与开发团队紧密协作，可使收益成倍增加。

运维为何与众不同

开发团队通常可以规划一个冲刺并加以保护。运维团队则面临源源不断的中断：事件、服务请求、安全补丁和紧急变更。严格的冲刺承诺往往在几天内就会被打破。敏捷仍然有帮助，但需要对实践进行调整。

工作类型示例典型做法
计划外停机、安全警报、紧急修复通过加急通道立即处理
例行请求新用户账户、权限变更尽可能标准化和自动化；通过看板流转
计划内改进升级数据库集群、实现备份自动化拆分为小条目并在待办事项列表中排定优先级
维护打补丁、证书续期作为周期性工作进行安排，并预留产能

适用于运维团队的敏捷实践

  • 带有 WIP 限制的 Kanban 看板： 可视化所有类型的工作并限制进行中的工作量；参见 WIP 限制.
  • 服务类别： 为事件设置加急通道，为有截止日期的工作设置固定日期通道，其余工作走标准通道；参见 Kanban 泳道.
  • 预留产能： 根据自身的历史数据，为计划外工作保留一部分产能，例如 30–40%。
  • 在看板前举行简短的每日站会： 关注受阻和积压时间长的条目。
  • 定期回顾和事后审查： 无责审查，并带来具体的改进。
  • 将自动化作为待办事项工作： 将重复性任务的自动化视为计划内的改进条目。
  • 与开发团队共担责任： 联合值班、共享指标和基础设施即代码；参见 DevOps.

如何在运维团队中引入敏捷

  1. 让所有工作可视化： 在两到四周内将事件、请求和项目放在同一个看板上，其他方面不做任何改变。
  2. 衡量工作构成： 统计计划外工作与计划内工作的比例。
  3. 设置服务类别和 WIP 限制： 商定哪些情况可以打断计划内工作的规则。
  4. 预留产能： 为您测量出的计划外工作预留足够的产能。
  5. 优先安排改进工作： 创建一个自动化和可靠性条目的待办事项列表，并指定明确的负责人。
  6. 建立节奏： 每周一次的补充会议和每两周一次的回顾会是不错的起点；参见 Kanban 节奏会议.
  7. 每月审查指标： 查看 周期时间, 吞吐量 和事件趋势，然后进行调整。

计算示例

一个六人的基础设施团队跟踪了四周的工作，发现已完成的条目中有 45% 是计划外工作。他们为计划外工作预留了约一半的产能，引入了一次只允许一个条目的加急通道，并为整个看板设置了 8 的 WIP 限制。他们每周从待办事项列表中拉取排在最前面的改进条目。两个月后，团队将三个最频繁的请求（旧系统的密码重置、测试环境搭建和日志访问申请）实现了自动化，计划外工作的比例降至约三分之一。标准请求的平均周期时间从八天缩短到四天。

敏捷运维的指标

指标重要性
各服务类别的周期时间反映每种类型的工作完成的速度
吞吐量反映团队每周完成的条目数量

平均服务恢复时间反映团队从事件中恢复的速度
变更失败率反映变更引发问题的频率
服务水平绩效反映是否达到了商定的目标；参见 服务级别协议

常见错误

  • 强迫以应对中断为主的团队做出两周的冲刺承诺。
  • 未将计划外工作放到看板上，导致团队明明很忙却看起来很闲。
  • 从不为改进工作留出时间，导致同样的事件反复发生。
  • 将敏捷与 IT 服务管理框架视为对立面；实际上，它们的流程可以与敏捷工作方式共存。
  • 将开发和运维割裂得过于彻底，以致问题被“扔过墙”给对方。

常见问题

IT 运维团队可以采用敏捷运维实践吗？

可以。他们会对其进行调整以处理计划外工作，通常采用 Kanban、预留产能并与开发团队紧密协作。

对于敏捷 IT 运维，Scrum 和 Kanban 哪个更好？

Kanban 通常更合适，因为它能处理持续不断的中断。以计划内项目工作为主的团队可以使用 Scrum。参见 Kanban 与 Scrum.

敏捷运维团队如何处理事件？

通过加急通道或服务类别，让紧急工作绕过正常队列，同时严格限制同时进行的加急条目数量。

敏捷运维与 DevOps 有什么区别？

敏捷运维是在运维团队内部应用敏捷实践； DevOps 将开发和运维结合起来，形成一种共同构建、发布和运行软件的方式。

敏捷运维团队应为计划外工作预留多少产能？

以自身的历史数据为依据。跟踪数周的工作，计算计划外工作的占比，并预留大致相当的产能。

敏捷 IT 运维能与 ITIL 配合使用吗？

可以。ITIL 描述的是服务管理实践；敏捷描述的是团队的工作方式。许多组织同时使用两者。

敏捷运维团队应跟踪哪些指标？

周期时间、吞吐量、计划内与计划外工作、服务恢复时间、变更失败率和服务水平绩效。

敏捷运维团队需要产品负责人吗？

许多团队受益于有人负责排定改进工作的优先级并平衡各类请求；有些组织称之为服务负责人。

敏捷运维团队如何开展站会？

在看板前简短进行，重点关注受阻、积压时间长和加急的条目，而不是逐人汇报状态。

敏捷运维中的无责事后审查是什么？

一种审查方式，关注的是系统和流程如何导致事件发生，而不是谁造成了事件，并商定改进措施。
