项目任务和活动：定义与示例

项目任务和活动是为产出项目可交付成果而进行排期、分配和跟踪的各项工作。活动是一个独特的、已排期的工作单元，具有持续时间、资源和明确的产出；“任务”通常指同一事物，或指活动内部更小的步骤。本指南解释两者的区别，展示如何定义活动并确定其规模，并逐步讲解一份完整的活动清单。

要点总结

  • PMI 将活动定义为一项独特的、已排期的工作部分；它没有正式定义“任务”。大多数工具把进度计划中的每一行都称为任务。
  • 活动来自工作包，即工作分解结构的最低层级。工作包描述产出；活动描述产生这些产出的工作。
  • 用动词加名词为每项活动命名，指定一名负责人，并设定一个可核查的完成标准。
  • 确定活动规模，使其能够被估算和跟踪：常见的经验法则是 8 至 80 小时的工作量，且不超过一个报告期。
  • 工作量和持续时间是不同的。根据负责人的实际可用时间进行相互换算。
  • 记录属性（ID、WBS 编码、紧前活动、持续时间、资源、制约因素），使活动清单能够转化为进度计划。

什么是项目活动和任务？

A 项目活动 是产出项目可交付成果所需的一项独特的、已排期的工作。它有明确的开始和完成、估算的持续时间、执行所需的资源以及可以核查的产出。 项目任务 要么是活动的另一种说法，要么（在团队加以区分时）是活动中更小的步骤。

《PMBOK 指南》将活动定义为在项目过程中执行的一项独特的、已排期的工作部分。“任务”一词不是 PMI 定义的术语，但大多数软件都使用这个词：Microsoft Project、Wrike、Asana 和大多数其他工具都把计划中的每一行称为任务。在实践中，您会遇到三种约定。

工作包与活动

工作包的描述依据是其 产出 （一个名词：“培训材料”）。活动则用以下方式描述： 工作 （一个动词：“编写培训幻灯片”）。WBS 止于工作包；活动清单从这里开始。这种划分使 WBS 聚焦于范围，活动清单聚焦于时间和工作量。

活动与里程碑

活动消耗时间和工作量。里程碑标志着某个时刻，例如一次审批或移交，没有持续时间。里程碑可用作检查点和报告，但不能为其分配工作。如果您发现自己写的是“里程碑：构建数据库”，那么它其实是一项活动。

活动和任务的类型

并非所有活动在进度计划中的表现都相同。了解其类型有助于您正确地估算和跟踪它们。

活动属性：应记录的内容

活动属性 是记录的每项活动的详细信息。初期只有少数几项；随着计划的推进会添加更多。《PMBOK 指南》列出了如下属性，大多数进度计划工具都为每项属性提供了字段：

  • 唯一 ID 和 WBS 编码，使成本和进度汇总到正确的工作包。
  • 名称 （动词加名词）和 描述 的工作。
  • 完成标准：您如何知道它已完成。
  • 紧前和紧后活动，注明关系类型以及任何提前量或滞后量；参见 紧前活动与紧后活动.
  • 工作量和持续时间估算，并附上估算依据。
  • 资源和负责人：所需的人员、技能、设备或材料，以及唯一的责任人。
  • 制约因素和强制日期，例如供应商交付日期。
  • 假设条件，例如“主题专家每周可投入两天”。
  • 存放位置 和 活动类型 （如适用）。

如何逐步定义活动

用 PMBOK 的术语来说，这就是 定义活动 过程，其主要产出是活动清单、活动属性和里程碑清单。通俗地说，您是在把每一部分范围转化为可以排期的工作清单。

  1. 从 WBS 开始。 逐个处理每个工作包。如果您还没有 WBS，请先建立一个；我们的 工作分解结构模板 为您提供了起始格式。
  2. 让执行工作的人参与进来。 询问他们完成该工作包需要哪些步骤。他们了解隐藏的工作，例如准备、评审和返工。
  3. 列出活动。 先头脑风暴，再整理。包括非建造类工作：评审、审批、采购前置时间、培训和移交。
  4. 为每项活动命名 ，以动词加名词的形式，并为其编写完成标准。
  5. 确定每项活动的规模 ，以便能够估算和跟踪（参见下文的规模规则）。拆分过大的活动；合并过于琐碎的活动。
  6. 添加里程碑 用于关键事件：审批、移交、外部交付、阶段结束。
  7. 记录属性 您现在需要的（至少包括 ID、WBS 编码、名称、负责人），并为排序和估算期间添加的属性留出空间。
  8. 审视清单 ，与工作包负责人一起进行。检查完成所有活动是否能产出整个工作包，且不包含其范围之外的内容。
提示

您不必在开始时就定义所有活动。 滚动式规划，如《PMBOK 指南》所述，是指对近期工作进行详细规划，对远期工作进行较高层次的规划，随着了解的加深再补充细节。对于周期较长的项目，这往往是务实的做法。

好的名称能让每个人都知道这项工作是什么，并暗示何时完成。使用 动词加名词，并且要足够具体，使两个人不会产生不同的理解。

不好的名称为何薄弱更好的名称

持续支持永远完不成提供上线支持（第 1 至 2 周）

为每个名称配上 完成标准：用一句话描述完成的证据，例如“报告已由发起人通过电子邮件批准”。如果写不出来，说明该活动可能过于模糊或过大。

任务应该多大？

过大的活动无法跟踪：它们连续数周显示“进行中”，然后要么完成，要么突然未能完成。过小的活动则会导致没人能维护的计划。以下经验法则可帮助您找到中间点：

  • 8/80 规则： 一项活动的工作量应在 8 至 80 小时之间。这是一条规划经验法则，而非标准，因此请将其作为参考。
  • 报告期原则： 活动的时长不应超过进度报告的间隔，通常为一到两周，这样每份报告都能显示真正的进展。
  • 单一负责人原则： 如果一项活动需要两个人负责，那它很可能是两项活动。
  • 估算原则： 如果执行者无法有把握地估算它，就进一步分解。
  • 有用性原则： 不要为只需几分钟的工作排期。把它们作为任务保留在负责人自己的清单上。

工作量与持续时间：计算实例

工作量是工作的人时数。持续时间是从开始到完成的工作日数。只有当某人全职从事该活动时两者才相等，而这种情况很少见。请根据负责人的实际可用时间将工作量换算为持续时间：

步骤计算结果
工作量估算设计师估算幻灯片和讲义36 小时
工作日标准工作日7.5 小时
可用率设计师在本项目上投入 60% 的时间7.5 x 0.6 = 每天 4.5 小时
工期36 / 4.58 个工作日

如果您把这 36 小时排成五天（36 / 7.5，向上取整），那么在工作开始之前计划就已经错了三天。

第 4 步：将活动分解为任务

  • 设置幻灯片模板和文件夹结构。
  • 编写模块 1 幻灯片（问候与倾听）。
  • 编写模块 2 幻灯片（处理投诉）。
  • 编写模块 3 幻灯片（跟进与升级）。
  • 编写学员讲义。
  • 对照大纲自查并发送评审。

执行设计解决方案；构建组件；采购设备；运行测试；培训用户；迁移数据
监控每周更新进度计划；评审问题日志；编写状态报告；评估变更请求
收尾获取验收签核；移交给运营部门；召开经验教训总结会；关闭合同；解散团队

项目管理工作本身（例如报告和会议）通常作为投入水平型任务或周期性任务来计划，而不是作为详细的活动。将其他工作所依赖的重大评审和决策会议作为活动或里程碑纳入。

从活动清单到进度计划

活动清单是其余进度规划工作的输入。通常的顺序是：

  1. 排列活动顺序 ，通过添加依赖关系；参见 任务依赖关系.
  2. 估算持续时间 ，根据工作量和可用时间。
  3. 分配资源 并检查是否存在过度分配；参见 资源分配.
  4. 制定进度计划，计算关键路径并将其显示在 甘特图.
  5. 为进度计划设定基准 一旦获批，即可据此衡量进度；参见 项目基准.

完整流程请参阅我们的指南： 项目进度安排.

敏捷项目中的任务

敏捷团队使用不同的层级结构，但理念相似。大块工作是 史诗，再拆分为 用户故事 ，交付有价值的东西。在 冲刺计划会期间，开发人员通常会将每个用户故事拆分为 任务：完成它所需的技术步骤，例如“编写 API 端点”或“更新帮助文本”。

  • 用户故事按相对大小估算（通常使用故事点）；任务如果要估算，通常以小时计。
  • 任务存放在 Sprint 待办事项列表 ，由开发人员负责，而不是由经理分配。
  • 任务在 Sprint 开始前适时创建，这就是在极短周期内进行的滚动式规划。
  • 完成情况依据以下标准判断： 完成的定义，起到完成标准的作用。

在项目期间管理任务

工作开始后，活动清单就变成了跟踪工具。以下几种做法能让它保持真实：

  • 至少每周更新： 记录实际开始和完成日期以及剩余持续时间，而不仅仅是一个百分比。
  • 谨慎对待完成百分比： “完成了 90%”可能连续几周都是如此。许多团队改用简单的约定，例如短活动采用 0/100（完成前不计入），或者 50/50（开始时计入一半，完成时计入另一半）。
  • 对照完成标准进行跟踪： 活动在满足其标准时才算完成，而不是在负责人停止工作时。
  • 重新规划，而不是覆盖： 如果某项活动需要更长时间，请修改其剩余持续时间，让进度计划显示其影响，而不是手动编辑日期。
  • 保持职责清晰： a RACI 矩阵 在多人共同参与一项活动时很有帮助。

电子表格适用于小型项目；我们的 项目跟踪器模板 已配备负责人、状态和日期列，可直接使用。对于规模较大或多项目的工作，具有依赖关系、工作负载视图和仪表板的工具可以节省大量手动工作。 Wrike是我们排名第一的工具，能很好地处理任务层级、依赖关系和甘特图；请在我们的排名中将其与其他选择进行比较： 项目管理工具.

常见问题

项目任务和项目活动有什么区别？

许多人交替使用这两个词。在加以区分时，活动是您要估算、关联和跟踪的已排期工作单元，任务则是其中更小的步骤。PMI 定义了“活动”，但没有定义“任务”；大多数软件把进度计划中的每一行都称为任务。

项目管理中的活动是什么？

为产出可交付成果所需的一项独特的、已排期的工作，具有开始、完成、持续时间、资源和可核查的产出。

项目活动的示例有哪些？

培训课程的“编写幻灯片和讲义”、“对支付模块运行系统测试”或“浇筑一楼楼板”。每一项都有明确的产出，可以估算并分配。

什么是项目活动清单？

项目中所有已排期活动的列表，包含其 ID、名称和范围描述。它是排序、估算和编制进度计划的起点。

什么是活动属性？

为每项活动记录的详细信息，例如 ID、WBS 编码、描述、紧前和紧后活动、持续时间、资源、制约因素、假设和负责人。它们随着规划的推进而增加。

项目活动应该有多大？

小到足以可靠地估算和跟踪。常见的经验法则是 8 至 80 小时的工作量，且不超过一个报告期。

工作包和活动有什么区别？

工作包是 WBS 的最低层级，描述的是产出。活动是产出它所需的工作。参见 工作包.

活动和里程碑有什么区别？

活动需要时间和工作量。里程碑标志着一个重要事件，例如一次审批，其持续时间为零。

如何为项目任务命名？

以动词开头并说出结果，例如“批准预算”或“安装服务器”，并为名称配上完成标准。

什么是汇总任务？

对子任务进行分组的父任务；其日期、工作量和成本由子任务汇总而来。 汇总活动（hammock activity） 是一个相关概念，跨越两个互不相关的活动。

什么是投入水平型活动？

没有自身产出、持续时间与其所支持工作相同的支持性工作，例如项目行政管理。进度按时间推移衡量。

会议应作为项目任务列入吗？

包括其他工作所依赖的重大评审和决策会议。例行会议通常作为周期性任务或投入水平型任务处理。

如何将项目分解为任务？

将工作分解结构细化到工作包，然后询问执行工作的人每个工作包需要哪些活动。为活动命名、确定规模并排序，然后在有用时将活动分解为个人任务。

敏捷中的项目任务也一样吗？

敏捷团队将 用户故事 在 Sprint Planning 期间拆分为任务。这些任务由开发人员负责，通常只需几小时而不是几天。
