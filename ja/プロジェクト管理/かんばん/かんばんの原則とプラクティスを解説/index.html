かんばんの原則とプラクティス：実践ガイド

かんばんの原則は、かんばんメソッドの指針となるルールです：現在行っていることから始める、進化的な変化を追求することに合意する、現在の役割と肩書を尊重する、あらゆるレベルでのリーダーシップを奨励する。これに加えて、3つのサービス提供の原則と、それらの考えを日々の習慣に変える6つの一般的なプラクティスがあります。このガイドでは、それぞれを説明し、Kanban Universityとかんばんガイドでリストがどう異なるかを示し、そのまま使える実例を紹介します。

要点

  • Kanban Universityの原則のページは4つの基礎的な原則を挙げていますが、より新しいOfficial Guideは3つの変更管理の原則と3つのサービス提供の原則をまとめています。
  • 6つの一般的なプラクティスは、可視化する、WIPを制限する、フローを管理する、ポリシーを明示する、フィードバックループを実装する、協調的に改善し実験的に進化する、です。
  • かんばんガイド（2025.5）はかんばんを3つのプラクティスに集約し、改善は小さく漸進的でなくてもよいとしています。これはかんばんメソッドとの実質的な違いです。
  • 原則は、なぜ穏やかに変えるのかを説明し、プラクティスは、毎日ボードの前で実際に行うことです。
  • WIP制限と明示的なポリシーが仕事の大半を担います。ボトルネックを明らかにし、改善を意見ではなく証拠の問題にします。
  • STATIKは、チームにかんばんを導入する際に原則をステップごとに適用する方法を提供します。

かんばんの原則とは何ですか？

かんばんの原則 とは、かんばんメソッドが変化をどのように導入し進化させるかを形作る信念です。現在のプロセスから始め、合意した小さなステップで改善し、既存の役割と肩書を維持し、誰でも改善をリードできるようにすると述べています。6つの かんばんのプラクティス は、仕掛中の作業を制限するなど、それらの原則を実行に移す具体的な活動です。

原則は憲法であり、プラクティスは運用ルールです。チームがプラクティスを機械的に守っていても、原則を無視すれば失敗することがあります。たとえば、意見を聞かれたこともない人々に新しいボードを押し付けるような場合です。

かんばんの4つの基礎的な原則

これらの原則は、かんばんが組織をどのように変えるかを表しています。内側から、同意を得て、一度に一歩ずつ。Kanban Universityの原則のページでは、この順に挙げられています。

1. 現在行っていることから始める

かんばんは、ホワイトボードに描いた理想的なプロセスではなく、すでにあるプロセスに適用します。承認待ちのような厄介な部分も含め、現在の作業が実際にどう流れているかを図示し、ボードに載せます。この手法は独自のプロセスを規定しません。

  • 適用の仕方： 作業を行う人々に話を聞き、最近のアイテム3～4件を依頼から提供まで追い、実際に通過した状態を描きます。
  • 例： ある財務チームは、請求書が「受領」「承認」「支払済み」と流れると考えています。10件の請求書をたどると、そのほとんどが何日も滞留していた隠れた「発注書待ち」の状態が見つかります。その状態が列になります。
  • 警告サイン： ボードに誰も知らない列がある、またはボードが実態と合わないため各自が個人的なリストを使っている。

2. 漸進的で進化的な変化を追求することに合意する

影響を受ける全員が、プロセスは一連の小さな変更を通じて改善され、それぞれの変更は証拠に基づいて維持するか元に戻すことに事前に合意します。かんばんはチームが変化を自分のものとすることに依存しているため、合意が重要です。合意がなければ、最初のWIP制限が窮屈に感じられたときに、取り組みは支持を失います。

  • 適用の仕方： キックオフで、何も最終決定ではないこと、各変更はレビューされること、どの変更も元に戻せることを明言します。
  • 例： サポートデスクを階層型に再編する代わりに、チームはまず「ブロックされたチケットはデイリーミーティングで取り上げる」というポリシーを1つ追加し、1か月後に効果を見直します。
  • 警告サイン： 管理職が同じ週に新しいワークフロー、新しいツール、新しい役割を発表する。

3. 現在のプロセス、役割、責任、肩書を尊重する

かんばんは、誰が何をするかを変えることから始めません。既存の役割を維持することで不安が減ります。Kanban Universityはこれを、変化に対するより幅広い支持を築く方法だと説明しています。後で役割を変える必要が生じた場合は、ボードからの証拠がその理由を示し、チームはそれに合意できます。

  • 適用の仕方： 初日は職名、報告ライン、承認の責任をそのまま維持し、フローに影響するならボード上の状態やポリシーとして示します。
  • 例： 法務レビュー担当者がボトルネックになっています。チームはレビューをなくすのではなく、一度にそこに届く量を制限し、どの種類の契約に本当にレビューが必要かに合意します。
  • 警告サイン： かんばんについての最初の話し合いが新しい役割についてである。

4. あらゆるレベルでのリーダーシップの行動を奨励する

改善のアイデアは、仕事に最も近い人々から生まれることがよくあります。かんばんは、新人から役員まで、誰もが問題に気づき、よく考えられた変更を提案できる環境を求めています。

  • 適用の仕方： 改善の列やリストを見える形で用意し、アイデアを出した人がチームの合意を得て実験を行うようにします。
  • 例： 若手の開発者が、ブロックされたカードのほとんどが共有のテスト環境1つを待っていることに気づき、1か月分のブロックのデータを集めて予約のポリシーを提案する。
  • 警告サイン： チームリーダーだけがボードやそのポリシーを変更する。

これら4つの原則は、なぜかんばんが多くの変革よりも抵抗が少ないのかを説明しています。より広い組織変革にどう組み込むかについては、当サイトの次のガイドをお読みください： アジャイルトランスフォーメーション.

サービス提供の原則

Kanban Universityは、チームのアウトプットを顧客に提供するサービスとして扱う3つの原則を加えています。

顧客のニーズと期待を理解し、それに焦点を当てる

サービスはその顧客によって評価されます。David J. Andersonはこれを顧客の目から見て「目的に適合している」ことと表現し、求めたものをどれだけ早く、どれだけ予測可能に得られるかといった顧客自身の基準を、改善する指標として使うことを提案しています。

例： 社内のITチームが、依頼者が平均修正時間よりも、修正がいつ届くかを知ることを重視していることに気づきます。チームは次を公表し始めます： サービスレベル期待値（たとえば、標準的な依頼の85%を5営業日以内に）。

仕事をマネジメントし、人々がその周りで自己組織化するようにする

作業アイテムは数え、サイズを見積もり、制限し、追跡できますが、ナレッジワークにおける人の時間と労力ははるかに予測しにくいものです。そこでかんばんは作業のフローをマネジメントし、チームがその周りで自ら組織化することを信頼します。管理職は「全員が何をしているか？」ではなく「何がブロックされているか？」を尋ねます。

例： デイリーミーティングでは、部屋を一周して個人のステータスを報告する代わりに、ボードを右から左へカードごとに確認していきます。当サイトの次のガイド： かんばんのケイデンス にアジェンダがあります。

サービスのネットワークとそのポリシーを定期的に見直す

ほとんどのチームは他のチームに依存し、他のチームもそのチームに依存しています。サービスクラスやWIP制限などのポリシーがネットワーク全体の振る舞いを決めるため、顧客と事業にとってより良い成果を得られるよう、定期的に見直し改善すべきです。

例： プロダクトチームとデータチームが、すべてのリリースが同じデータ移行のステップを待っていることに気づきます。月次の合同レビューで、移行のスケジューリングについての共通のポリシーと、同時に実行できる数の明示的な上限に合意します。

かんばんの3つのアジェンダと9つの価値

かんばんメソッドの論者は、3つのアジェンダ、つまり組織がかんばんを導入しうる目的も説明しており、それぞれが3つの価値に結び付いています。Mike Burrowsが2014年のInfoQの連載記事でこれらを示し、Kanban Universityの研修でも取り上げられています。チームがなぜかんばんを導入するのかを説明するのに役立ちますが、原則やプラクティスほど頻繁には引用されません。

アジェンダ何についてのものか関連する価値
サステナビリティ需要と能力のバランスを取ることで、過重な負担を抱える個人やチームを楽にする透明性、バランス、協働
サービス志向顧客と、そのニーズを満たすサービスの流れに外向きの目を向ける顧客重視、フロー、リーダーシップ
存続可能性環境の変化に応じて進化し続けられる、適応力のある組織を築く理解、合意、尊重

ほとんどのチームはサステナビリティのアジェンダ（「私たちは過負荷だ」）から始め、顧客に期待値を公表するにつれてサービス志向へと移っていきます。

かんばんメソッドの6つの一般的なプラクティス

プラクティスは、原則が習慣になる場所です。おおむねチームが採用する順に並んでいますが、互いに補強し合っています。可視化によってどこでWIPを制限すべきかがわかり、WIP制限によってフローの問題が見えるようになり、明示的なポリシーによって改善が可能になります。

1. 作業、ワークフロー、ビジネスリスクを可視化する

見えない作業を見えるようにします。すべてのアイテムはカード、すべての状態は列であり、リスクは色、マーカー、スイムレーンで示します。Kanban Universityの表現には次が含まれます： ビジネスリスク（多くのチームが忘れがちなもの）：カードの種類、期日、遅延コストはひと目でわかるようにすべきです。

  1. 計画外の作業や内部の作業も含め、チームが行うすべての種類の作業を書き出します。
  2. 追跡したアイテムから得た状態を列として描き、作業が待つ箇所では、混雑した状態を「作業中」と「完了」に分けます。
  3. 現在のすべての項目を次に載せる： カンバンカード を開始日とともに記載します。
  4. リスクのマーカーを追加し、次を使います： スイムレーン は、特急レーンのように、意思決定に役立つ場合にのみ使います。

2. 仕掛中の作業を制限する

WIP制限は、ある状態、状態のグループ、またはシステム全体に入れられるアイテムの数に上限を設けます。これによりプルシステムが生まれ、キャパシティが空いたときだけ新しい作業が始まります。Kanban Universityは、引き込みに使う正確な仕組みよりも、制限そのもののほうが重要だとしています。

実例：最初のWIP制限を設定する。 6人のソフトウェアチームには、アナリスト1人、開発者4人、テスター1人がいます。今日のボードには、「分析」に3アイテム、「開発」に9アイテム、テスト待ちに6アイテムがあります。

状態人材現在のアイテム数初期のWIP制限理由
分析132作業中1件と、引き渡し準備のできた1件
開発495開発者1人あたり約1アイテム、加えてペア作業やブロックされたアイテム用に1
テスト待ち（待ち行列）-63制約の手前の小さなバッファ
テスト1-2テスターが制約であり、その集中を守る

「テスト待ち」が満杯の間、開発者は新しいアイテムに着手するのをやめ、テストやチェックの自動化を手伝います。これは、すべてをボトルネックに従属させるという制約理論の考え方です。当サイトの次のガイドを参照してください： 制約理論.

うまくいく理由を数字で。 リトルの法則によれば、安定したシステムでは、平均サイクルタイムはおおよそ平均WIPを平均スループットで割ったものです。チームが週に3アイテムを完了し、15アイテムを仕掛中にしていれば、平均的なアイテムは約15 ÷ 3 = 5週間かかります。同じスループットで仕掛中を8にすれば、約8 ÷ 3 ≈ 2.7週間になります。誰も働く量を増やしておらず、アイテムの待ち時間が減っただけです。

3. フローを管理する

フローの管理とは、作業がどう動くかを観察し、動かないときに対処することです：障害を取り除き、滞留しているアイテムを完了させ、待ち行列を平準化します。Kanban Universityの言葉を借りれば、目指すのは速く、滑らかに、予測可能に流れる仕事です。

  1. 毎日、仕掛中で最も古いアイテムとブロック中の印が付いたアイテムを探します。
  2. ボードの右側から始めて、それぞれを動かすには何が必要かを尋ねます。
  3. 期待値を超えそうなアイテムにスウォーミングする。参考： アジャイルのスウォーミング.
  4. 開始日と完了日を記録して、次を測定できるようにする： サイクルタイム と スループット.
  5. 次を注視する： WIPエイジングチャート と 累積フロー図 で、待ち行列の増大を確認します。

例： ほとんどのアイテムは「レビュー」を2日で通過するのに、あるカードが6日間「レビュー」にとどまっています。デイリーミーティングで、レビュー担当者がテストアカウントを待っていることがわかります。1人がすぐにそれを申請し、カードは翌日に完了し、コミットメントポイントでアカウントを申請するポリシーが追加されます。

4. ポリシーを明示する

ポリシーは、チームが従って働くルールです。Kanban Universityの言葉を借りれば、文書化して見える状態にすることで、改善についての議論が感情や逸話ではなく、合理的で証拠に基づいたものになります。Official Guideは典型的な例として、プル基準、WIP制限、サービスクラスを挙げています。

ポリシー記述例役立つ理由
「準備完了」への投入（コミットメントポイント）依頼者が明記され、受入基準があり、サイズが小または中である曖昧な作業がシステムに入るのを防ぐ
ブロックされたアイテム赤のタグを付け、理由と日付を追記し、次のデイリーミーティングで取り上げる障害を見える化し、測定可能にする
特急のサービスクラス一度に1枚。WIP制限を超えてもよい。本番環境のインシデントにのみ使用フローを壊さずに緊急の作業を通せる
「完了」からの退出次を満たす： 完成の定義 し、依頼者に伝えられている「完了」の意味に合意する

ポリシーは短くし、それが適用される列の横にボード上で掲示し、変更は合意によってのみ行います。サービスクラスと補充のルールについては、当サイトの次のガイドで扱っています： かんばんの計画.

5. フィードバックループを実装する

フィードバックループとは、チームが期待したことと実際に起きたことを比較して調整する、定期的な会議やレビューのことで、ケイデンスとも呼ばれます。Official Guide to the Kanban Methodは、出発点として次のチームレベルのケイデンスを提案しています：

ケイデンス推奨される頻度主に役立つプラクティス
チームのかんばんミーティング毎日フローを管理する：障害、滞留しているアイテム、今日何を完了できるか？
社内チームの補充ミーティング毎週、または必要に応じてWIPを制限し、ポリシーを明示する：何が「準備完了」に入るか、そしてその理由
チームのレトロスペクティブ2週間ごとまたは毎月協調的に改善する：データを見直し、実験に合意する

複数のチームやサービスが関わる場合は、サービス提供、オペレーション、リスク、戦略のレビューなど、サービス指向のケイデンスを加えます。可能な限り、すでに開いている会議を再利用しましょう。それが現在のプロセスを尊重することになります。

6. 協調的に改善し、実験的に進化する

変更は協力して行い、実験として扱います。Kanban Universityは、制約理論、深遠なる知識の体系、リーン経済モデルなどのモデルを使って変更の効果を予測し、その予測を実際の結果と比較することを提案しています。失敗しても安全な実験を、一度に1つずつ行います。

実験カードの例：

  • 観察： サイクルタイムの85パーセンタイルは12日で、カードは「レビュー待ち」で平均3日待っている。
  • 仮説： 「レビュー」を2に制限し、レビューをペアで行えば、スループットを変えずに、85パーセンタイルが6週間以内に約9日まで下がる。
  • 測定： （ボードから得たサイクルタイムのパーセンタイルと週ごとのスループット）。
  • レビュー日とロールバック： 6週間後のレトロスペクティブで見直す。スループットが週に1アイテム以上落ちたら元に戻す。

データの出典： ブロッカークラスタリング と フロー効率 は、実験の良い材料になります。

かんばんガイドの3つのプラクティスの比較

John ColemanとDaniel Vacantiが著したかんばんガイドは、それとは別の、より短い定義です。2025.5版（2025年5月）では、かんばんをプロセスを通じた価値のフローを最適化するための戦略と定義し、3つのプラクティスを説明しています：ワークフローを定義し可視化する、ワークフロー内のアイテムを積極的に管理する、ワークフローを改善する。各チームは1つ目を次に記録します： ワークフローの定義。作業アイテム、開始点と終了点、状態、WIPのコントロール方法、明示的なポリシー、サービスレベル期待値を含める必要があります。

かんばんガイドのプラクティス最も近いかんばんメソッドのプラクティスかんばんガイドが追加しているもの
ワークフローを定義し可視化する可視化する。ポリシーを明示するSLEを含む、文書化されたワークフローの定義（Definition of Workflow）
ワークフロー内のアイテムを積極的に管理するWIPを制限し、フローを管理するWIPのコントロール、不要な滞留の防止、作業のブロック解除への明確な焦点
ワークフローを改善するフィードバックループを実装する。協調的に改善し、実験的に進化する改善はジャストインタイムで行え、必須の会議はない

知っておくべき違いが2つあります。第一に、かんばんガイドには変更管理の原則がなく、必須の役割や会議もありません。第二に、改善は小さく漸進的でなくてもよいとしているのに対し、かんばんメソッドはチームに進化的な変化に合意するよう求めています。私たちの経験では、小さな変更のほうが今でも安全な既定の選択肢ですが、明らかに壊れているポリシーはすぐに直してよいというかんばんガイドの見方は、もっともな注意喚起です。

かんばんガイドは、WIP、スループット、作業アイテムの経過時間、サイクルタイムという4つのフローメトリクスも求めています。当サイトの かんばんのメトリクス ガイドでは、それらの計算方法とグラフ化の方法を示しています。

STATIKを使ってかんばんの原則をステップごとに適用する方法

Kanban Universityは、原則を尊重したかんばんシステムを設計するために、STATIK（Systems Thinking Approach to Introducing Kanban）を推奨しています。Official Guideには6つのステップが挙げられています。チームのためにではなく、チームと一緒に行いましょう。このガイドは、プロジェクトマネージャー、チームリーダー、コーチが1人でSTATIKを行うことを特に戒めています。

  1. 不満の原因を特定する。 納期の遅れ、過負荷、予測できないことなど、チームとその顧客が何に不満を感じているかを尋ねます。アウトプット：彼ら自身の言葉で書かれた問題の短いリスト。
  2. 需要を分析する。 届く作業の種類、その出どころ、おおよその頻度を列挙します。アウトプット：到着率付きの作業アイテムの種類。
  3. システムの能力を分析する。 チームが現在どれだけ提供し、アイテムにどれだけ時間がかかっているかを見ます。アウトプット：大まかでもよいので、基準となるスループットとサイクルタイム。
  4. ワークフローをモデル化する。 待ち行列を含め、各種類の作業が通過する状態を図示します。アウトプット：ボードの列と、コミットメントポイントおよびデリバリーポイント。
  5. サービスクラスを特定する。 特急、期日固定、標準、無形など、緊急度の種類ごとの扱いに合意します。アウトプット：ポリシー付きのサービスクラス。
  6. かんばんシステムを設計する。 WIP制限、ポリシー、ケイデンス、ボードのレイアウト、追跡する指標を設定します。アウトプット：機能するボードと会議のカレンダー。

ステップ1～3は、「現在行っていることから始める」が実践される段階です。ステップ4～6でプラクティスが生まれます。ステップ4の前にフローをより詳しく図示するには、 バリューストリームマップ が役立ち、当サイトの無料の ワークフローのテンプレート では、状態と担当者を記録する場所を用意しています。

よくある質問

カンバンの4つの原則とは何ですか？

Kanban Universityの原則のページには次が挙げられています：現在行っていることから始める、漸進的で進化的な変化を追求することに合意する、現在のプロセス、役割、責任、肩書を尊重する、あらゆるレベルでのリーダーシップの行動を奨励する。

かんばんの6つのプラクティスとは何ですか？

可視化する、仕掛中の作業を制限する、フローを管理する、ポリシーを明示する、フィードバックループを実装する、協調的に改善し実験的に進化する。

なぜかんばんの原則を6つとする情報源があるのですか？

Kanban UniversityのOfficial Guideは、3つの変更管理の原則（現在行っていることから始める、進化的な変化を通じた改善を追求することに合意する、あらゆるレベルでのリーダーシップを奨励する）と3つのサービス提供の原則をまとめています。現在の役割の尊重は1つ目に組み込まれています。

かんばんのサービス提供の原則とは何ですか？

顧客のニーズと期待を理解し、それに焦点を当てる。仕事をマネジメントし、人々がその周りで自己組織化するようにする。そして成果を改善するため、サービスのネットワークとそのポリシーを定期的に見直す。

最も重要なかんばんの原則は何ですか？

Kanban Universityは順位を付けていません。実際には、現在行っていることから始めることが土台であり、WIPの制限が通常フローに最も大きな違いをもたらすプラクティスです。

かんばんにおける「現在行っていることから始める」とはどういう意味ですか？

既存のプロセスにかんばんを適用するという意味です。新しいプロセスを先に設計するのではなく、現在の作業が実際にどう流れているかを図示し、段階的に改善します。

かんばんにおけるフィードバックループとは何ですか？

チームが期待した結果と実際の結果を比較して調整する、定期的な会議やレビュー。Kanban Universityは、毎日のかんばんミーティング、毎週または必要に応じた補充ミーティング、2週間ごとまたは毎月のレトロスペクティブを提案しています。

かんばんガイドの3つのプラクティスとは何ですか？

かんばんガイド 2025.5は、ワークフローを定義し可視化する、ワークフロー内のアイテムを積極的に管理する、ワークフローを改善する、を挙げています。

かんばんの3つのアジェンダとは何ですか？

サステナビリティ、サービス志向、存続可能性です。それぞれが3つの価値に結び付いています：透明性、バランス、協働。顧客重視、フロー、リーダーシップ。理解、合意、尊重。

かんばんの原則はスクラムの価値基準とどう違いますか？

スクラムの5つの価値基準は、定められたフレームワークの中でスクラムチームがどう振る舞うかを表します。かんばんの原則は、新しいプロセスを押し付けずに既存のプロセスを徐々に進化させる方法を表します。参考： かんばんとスクラムの比較.
