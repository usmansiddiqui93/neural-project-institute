プロジェクトのタスクとアクティビティ：定義と例

プロジェクトのタスクとアクティビティとは、プロジェクトの成果物を生み出すためにスケジュールし、割り当て、追跡する個々の作業です。アクティビティは、所要期間、資源、明確なアウトプットを持つ、明確に区別されスケジュールに組み込まれた作業単位です。「タスク」は同じ意味で使われることも、アクティビティ内のより小さなステップを指すこともあります。このガイドでは、両者の違いを説明し、アクティビティの定義と規模の決め方を示し、アクティビティ・リストの完全な例を順を追って紹介します。

要点

  • PMIはアクティビティを、明確に区別されスケジュールに組み込まれた作業の一部と定義していますが、「タスク」は正式に定義していません。ほとんどのツールでは、スケジュールの各行をタスクと呼んでいます。
  • アクティビティは、WBSの最下位レベルであるワークパッケージから生まれます。ワークパッケージはアウトプットを記述し、アクティビティはそれを生み出す作業を記述します。
  • 各アクティビティに動詞と名詞で名前を付け、1人の担当者と確認可能な完了基準を定めます。
  • アクティビティは見積りと追跡ができる規模にします。一般的な目安は工数8～80時間で、1報告期間を超えないことです。
  • 工数と所要期間は別物です。担当者の実際の稼働可能時間を使って、一方を他方に換算します。
  • アクティビティ・リストをスケジュールにできるよう、属性（ID、WBSコード、先行作業、所要期間、資源、制約条件）を記録します。

プロジェクトのアクティビティとタスクとは何ですか？

A プロジェクトのアクティビティ とは、プロジェクトの成果物を生み出すために必要な、明確に区別されスケジュールに組み込まれた作業です。明確な開始と終了、見積もられた所要期間、実施に必要な資源、確認可能なアウトプットを持ちます。 プロジェクトのタスク は、アクティビティの別名であるか、チームが区別している場合はアクティビティ内のより小さなステップです。

PMBOKガイドでは、アクティビティを、プロジェクトの過程で実施される、明確に区別されスケジュールに組み込まれた作業の一部と定義しています。「タスク」はPMIの定義された用語ではありませんが、ほとんどのソフトウェアで使われている言葉です。Microsoft Project、Wrike、Asanaなど多くのツールは、計画の各行をタスクと呼んでいます。実際には、3つの慣例に出会うことになります。

アクティビティとタスク：簡単な答え

慣例言葉の使われ方表れる場所
区別せずに使われるアクティビティとタスクは同じ意味：スケジュール上の作業単位ほとんどの組織とスケジューリングツール
アクティビティがタスクを含むアクティビティはスケジュールされ追跡されるもので、タスクはその中のステップであり、多くの場合作業者自身が管理する大規模プロジェクト、PMI式の計画、多くの教科書
タスクがアクティビティを含むタスクがスケジュール上の項目で、アクティビティはそれを完了するために人が行うこと一部の組織や一部のソフトウェア（あまり一般的ではない）

どれも間違いではありません。重要なのは、プロジェクトで1つの慣例を一貫して使うことです。このガイドでは2番目を使います： アクティビティ は見積り、関連付け、報告を行うスケジュール上の単位で、 タスク は、担当者がアクティビティを完了するために使う、より小さなステップです。チームがこれらの言葉を区別せずに使っている場合は、本ガイド全体を通して「アクティビティ」と「タスク」を同じものとして読んでください。

ワークパッケージとアクティビティの違い

ワークパッケージは アウトプット （名詞：「研修資料」）によって記述されます。アクティビティは 作業 （動詞：「研修スライドを作成する」）によって記述されます。WBSはワークパッケージで終わり、アクティビティ・リストはそこから始まります。この分離により、WBSはスコープを、アクティビティ・リストは時間と工数を扱うものに保たれます。

アクティビティとマイルストーンの違い

アクティビティは時間と労力を消費します。マイルストーンは承認や引き渡しなどの瞬間を示し、所要期間はありません。マイルストーンはチェックポイントや報告に役立ちますが、作業を割り当てることはできません。「マイルストーン：データベースを構築する」と書いているなら、それはアクティビティです。

アクティビティとタスクの種類

すべてのアクティビティがスケジュール上で同じように振る舞うわけではありません。種類を知っておくと、正しく見積もり、追跡できます。

アクティビティ属性：記録すべきもの

アクティビティ属性 は、各アクティビティについて記録される詳細情報です。初期の段階では少数ですが、計画が進むにつれて追加されます。PMBOKガイドには次のような属性が挙げられており、ほとんどのスケジューリングツールにはそれぞれのフィールドがあります：

  • 一意のID と WBSコード。これにより、コストと進捗が正しいワークパッケージに集計されます。
  • 名称 （動詞＋名詞）と 説明 です。
  • 完了基準：完了したことをどうやって判断するか。
  • 先行作業と後続作業を、リンクの種類とリードやラグとともに設定します。詳しくは 先行アクティビティと後続アクティビティ.
  • 工数と所要期間の見積りに見積り根拠を添えて行います。
  • 資源と担当者：必要な人員、スキル、機器、資材と、説明責任を負う1人の担当者。
  • 制約条件と指定日。たとえばサプライヤーの納期などです。
  • 前提条件。たとえば「専門家が週2日対応可能」などです。
  • 保管場所 と アクティビティの種類 （該当する場合）。

アクティビティを定義する手順

PMBOKの用語では、これは アクティビティの定義 プロセスで、主なアウトプットはアクティビティ・リスト、アクティビティ属性、マイルストーン・リストです。平たく言えば、スコープの各部分をスケジュール可能な作業のリストに変えることです。

  1. WBSから始める。 ワークパッケージを1つずつ取り上げます。まだWBSがなければ、先に作成しましょう。当サイトの WBSテンプレート が、出発点となる形式を提供します。
  2. 作業を行う人を巻き込みます。 ワークパッケージを作り上げるのに必要なステップを担当者に尋ねます。担当者は、準備、レビュー、手戻りといった見えにくい作業を知っています。
  3. アクティビティを列挙します。 まずブレインストーミングし、それから整理します。レビュー、承認、調達のリードタイム、トレーニング、引き渡しなど、構築以外の作業も含めます。
  4. 各アクティビティに名前を付ける を動詞＋名詞で付け、完了基準を書きます。
  5. 各アクティビティの規模を決める し、見積りと追跡ができるようにします（下記の規模のルールを参照）。大きすぎるアクティビティは分割し、ささいなほど小さいものは統合します。
  6. マイルストーンを追加する を、承認、引き渡し、外部からの納品、フェーズ終了などの重要なイベントに設定します。
  7. 属性を記録する を今必要な分だけ（少なくともID、WBSコード、名称、担当者）記録し、順序付けと見積りの段階で追加される属性の余地を残しておきます。
  8. リストを見直す を、ワークパッケージの担当者と行います。すべてのアクティビティを完了するとワークパッケージ全体が完成し、その範囲外のものは何も含まれないことを確認します。
ヒント

最初にすべてのアクティビティを定義する必要はありません。 ローリングウェーブ計画法は、PMBOKガイドで説明されているもので、近い将来の作業は詳細に、先の作業は大まかに計画し、分かってくるにつれて詳細を加えていく方法です。長期のプロジェクトでは、これが誠実なアプローチであることが多いです。

タスクとアクティビティの名前の付け方

良い名前は、その作業が何であるかを全員に伝え、いつ完了するかを示唆します。 動詞＋名詞、そして2人の人が異なる解釈をしない程度に具体的であるべきです。

悪い名前弱い理由より良い名前
テスト動詞がない、スコープがない、終点がない決済モジュールのシステムテストを実施する
継続的なサポートいつまでも終わらない本番稼働のサポートを提供する（第1～2週）
サラの業務作業ではなく人の名前になっているサプライヤー契約の草案
ウェブサイトそれはアクティビティではなく成果物商品一覧ページを構築する
予算を見るアウトプットが不明確フェーズ2の予算を承認する
ミーティングどれを、なぜ選ぶのか？設計承認レビューを開催する

各名前に 完了基準：完了したことを示す証拠を記述する1文。たとえば「報告書がスポンサーにメールで承認された」など。書けない場合、そのアクティビティはおそらく曖昧すぎるか大きすぎます。

タスクの大きさはどのくらいにすべきですか？

大きすぎるアクティビティは追跡できません。何週間も「進行中」と表示され、その後完了するか、突然完了しなくなります。小さすぎるアクティビティは、誰も維持できない計画を生みます。次の目安が、その中間を見つける助けになります：

  • 8/80ルール： アクティビティの工数は8～80時間にすべきです。これは計画上の経験則であり基準ではないので、目安として扱いましょう。
  • 報告期間のルール： アクティビティは進捗報告の間隔（多くの場合1～2週間）より長くすべきではありません。そうすれば、各報告で実際の進み具合が分かります。
  • 1人の担当者ルール： 1つのアクティビティに説明責任者が2人必要なら、それはおそらく2つのアクティビティです。
  • 見積りのルール： 実施する人がそれなりの確信を持って見積もれない場合は、さらに分解します。
  • 有用性のルール： 数分で終わる作業はスケジュールに入れません。担当者自身のリストのタスクとして管理します。

工数と所要期間：計算例

工数は作業の人時の数です。所要期間は開始から終了までの稼働日数です。両者が等しくなるのは、誰かがそのアクティビティにフルタイムで取り組む場合だけで、それはまれです。担当者の実際の稼働可能時間を使って、工数を所要期間に換算します：

ステップ計算結果
工数見積りデザイナーがスライドと配布資料を見積もる36時間
稼働日標準的な1日7.5時間
稼働率デザイナーはこのプロジェクトに60%の割合で従事7.5 x 0.6 = 1日4.5時間
所要期間36 / 4.58稼働日

36時間を5日（36 / 7.5を切り上げ）としてスケジュールしていたら、作業が始まる前から計画は3日ずれていたことになります。

ステップ4：アクティビティをタスクに分解する

インストラクショナルデザイナーは、A3を個人のタスクリストに落とし込みます。これらは個別にスケジュールされるものではなく、担当者が36時間を管理するのに役立ちます：

  • スライドテンプレートとフォルダー構成を用意する。
  • モジュール1のスライド（挨拶と傾聴）を作成する。
  • モジュール2のスライド（苦情対応）を作成する。
  • モジュール3のスライド（フォローアップとエスカレーション）を作成する。
  • 参加者用の配布資料を作成する。
  • アウトラインに照らして自己チェックし、レビューに回す。

当サイトの ToDoリストテンプレート はこのようなタスクリストに適しており、アクティビティ・リスト自体は プロジェクトスケジュールテンプレート.

アクティビティ・リストからスケジュールへ

アクティビティ・リストは、その後のスケジュール計画のインプットになります。通常の流れは次のとおりです：

  1. アクティビティを順序付ける を依存関係を加えて行います。詳しくは タスクの依存関係.
  2. 所要期間を見積もる を、工数と稼働可能時間から算出します。
  3. 資源を割り当てる を行い、過剰割り当てがないか確認します。詳しくは リソース配分.
  4. スケジュールを作成する、クリティカルパスを計算し、それを ガントチャート.
  5. スケジュールのベースラインを設定する 承認後、進捗をこれと比較して測定できるようにします。詳しくは プロジェクトのベースライン.

プロセス全体については、当サイトのガイド プロジェクトのスケジューリング.

アジャイルプロジェクトにおけるタスク

アジャイルチームは別の階層を使いますが、考え方は似ています。大きな作業は エピック、それがさらに ユーザーストーリー （価値あるものを提供するもの）に分解されます。 スプリントプランニングでは、開発者が各ストーリーを タスク：完了に必要な技術的なステップ。たとえば「APIエンドポイントを書く」「ヘルプテキストを更新する」など。

  • ストーリーは相対的に規模を見積もり（多くの場合ストーリーポイントで）、タスクは見積もる場合でも通常は時間単位です。
  • タスクは スプリントバックログ 、マネージャーが割り当てるのではなく開発者が担当します。
  • タスクはスプリントに合わせてジャストインタイムで作成されます。これは非常に短いサイクルで行うローリングウェーブ計画です。
  • 完了は次に照らして判断されます： 完成の定義。これが完了基準の役割を果たします。

プロジェクト期間中のタスク管理

作業が始まると、アクティビティ・リストは追跡ツールになります。いくつかの実践で、リストを正直に保てます：

  • 少なくとも毎週更新する： パーセンテージだけでなく、実際の開始日・終了日と残りの所要期間を記録します。
  • 完了率には注意が必要です： 「9割完了」は何週間もそのままのことがあります。多くのチームは代わりに、短いアクティビティには0/100（完了するまで計上なし）、または50/50（開始時に半分、終了時に半分を計上）といったシンプルな慣例を使っています。
  • 完了基準に照らして追跡する： アクティビティは、担当者が作業をやめたときではなく、基準が満たされたときに完了します。
  • 上書きせずに再計画する： アクティビティが長引きそうなときは、日付を手作業で編集するのではなく、残りの所要期間を変更し、スケジュールにその影響を示させます。
  • 担当を明確に保つ： a RACIマトリクス は、複数の人が1つのアクティビティに関わる場合に役立ちます。

小規模なプロジェクトならスプレッドシートで十分です。当サイトの プロジェクトトラッカーテンプレート には、すぐに使える担当者、ステータス、日付の列があります。大規模な作業や複数プロジェクトの作業では、依存関係、ワークロードビュー、ダッシュボードを備えたツールで多くの手作業を省けます。 Wrikeは当サイトで第1位のツールで、タスクの階層、依存関係、ガントチャートをうまく扱えます。当サイトのランキングで代替ツールと比較してください： プロジェクト管理ツール.

よくある質問

プロジェクトのタスクとアクティビティの違いは何ですか？

多くの人はこれらを区別せずに使っています。区別する場合、アクティビティは見積り、関連付け、追跡を行うスケジュール上の作業単位で、タスクはその中のより小さなステップです。PMIは「アクティビティ」を定義していますが、「タスク」は定義していません。ほとんどのソフトウェアでは、スケジュールの各行をタスクと呼んでいます。

プロジェクトマネジメントにおけるアクティビティとは何ですか？

成果物を生み出すために必要な、明確に区別されスケジュールに組み込まれた作業で、開始、終了、所要期間、資源、確認可能なアウトプットを持ちます。

プロジェクトのアクティビティの例にはどのようなものがありますか？

研修コースの「スライドと配布資料を作成する」、「決済モジュールのシステムテストを実施する」、「1階のスラブを打設する」などです。それぞれに明確なアウトプットがあり、見積りと割り当てが可能です。

プロジェクトのアクティビティリストとは何ですか？

プロジェクトでスケジュールされたすべてのアクティビティを、ID、名称、スコープの説明とともにまとめた一覧です。順序付け、見積り、スケジュール作成の出発点になります。

アクティビティ属性とは何ですか？

各アクティビティについて記録される詳細情報で、ID、WBSコード、説明、先行・後続作業、所要期間、資源、制約条件、前提条件、担当者などです。計画が進むにつれて増えていきます。

プロジェクトのアクティビティはどのくらいの大きさにすべきですか？

確実に見積もり、追跡できる程度に小さくします。一般的な目安は工数8～80時間で、1報告期間を超えないことです。

ワークパッケージとアクティビティの違いは何ですか？

ワークパッケージはWBSの最下位レベルで、アウトプットを記述します。アクティビティは、それを生み出すために必要な作業です。詳しくは ワークパッケージ.

アクティビティとマイルストーンの違いは何ですか？

アクティビティには時間と労力がかかります。マイルストーンは承認などの重要なイベントを示し、所要期間はゼロです。

プロジェクトのタスクにはどのように名前を付けますか？

「予算を承認する」「サーバーを設置する」のように、動詞で始めて結果を示し、名前と完了基準を組み合わせます。

サマリータスクとは何ですか？

サブタスクをまとめる親タスク。日程、工数、コストはサブタスクから集計されます。 ハンモック活動 は、無関係な2つのアクティビティの間にまたがる関連概念です。

作業量型アクティビティとは何ですか？

プロジェクトの管理業務など、独自のアウトプットを持たず、支援対象の作業と同じ期間続く支援作業です。進捗は時間の経過で測定します。

会議はプロジェクトのタスクに含めるべきですか？

他の作業が依存する主要なレビューや意思決定の会議を含めます。定例会議は通常、繰り返しタスクまたは作業量型のタスクとして扱います。

プロジェクトをタスクに分解するにはどうすればよいですか？

ワークパッケージまでのWBSを作成し、作業を行う人に各パッケージに必要なアクティビティを尋ねます。それらに名前を付け、規模を見積もり、順序付けし、必要に応じてアクティビティを個人のタスクに分解します。

アジャイルでもプロジェクトのタスクは同じですか？

アジャイルチームは ユーザーストーリー をスプリントプランニングでタスクに分解します。タスクは開発者が担当し、通常は数日ではなく数時間で終わります。
